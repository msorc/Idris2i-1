# Changelog Next

This CHANGELOG describes the merged but unreleased changes.  Please see
[CHANGELOG](./CHANGELOG.md) for changes to all previously released versions of
Idris2, as well as the sub-headings typically used for changes.  All new PRs
should target this file (`CHANGELOG_NEXT`).

## [Next version]

### Documentation

* Various changes to user documentation both the frontend and backend,
  as generated by ReadTheDocs and located in `doc`.

  + Fixed incorrect `plus` function in %transform section of pragma docs.

  + Migrated sphinx python project to
    [`uv`](https://docs.astral.sh/uv/)
    for better project management.

  + Adopted sphinx extension
    [`myst-parser`](https://myst-parser.readthedocs.io/en/latest/)
    to enable documentation to be provided using Markdown,
    specifically the [`MyST`](https://mystmd.org/) dialect.

  + Adopted,
    but not activated,
    inclusion of
    [`sphinx-contrib.bibtex`](https://github.com/mcmtroffaes/sphinxcontrib-bibtex)
    to provide better support for citing in documentation.

  + Adopted a new sphinx theme called
    [`sphinx_book_theme`](https://sphinx-book-theme.readthedocs.io),
    which provides a HTML theme with a more 'modern' look & feel.
    For example,
    more indepth navigation,
    revised responsive mode (when compared to ReadTheDocs),
    and
    light & dark modes.

  + Removed the ReadTheDocs theme options `display_version` and
    `prev_next_buttons_location`, which `sphinx_book_theme` does not support,
    and made `make` in `docs/` treat Sphinx warnings as errors
    (`SPHINXOPTS` defaults to `-W --keep-going`).

  + The FFI overview no longer says that the run time frees the `char*` that
    a C function returns as a `String`: no backend does (measured with Chez
    and RefC), it is copied and left alone, so that a function may return a
    string that it keeps (`getenv`, a literal).  The overview now says so,
    shows how to bind a function whose result the caller must free (a
    `Ptr String` that is converted and then freed) without leaking it, and
    says that a `String` argument is only valid until the C function returns.
    [#2455](https://github.com/idris-lang/Idris2/issues/2455)

  + The FFI overview says how several specifiers of `%foreign` are written
    (one per line, or after a string literal on the same line), what C type `Int` is (`int` with the Scheme backends, `int64_t` with
    RefC), what a `NULL` returned as a `String` does, and how long a callback
    lives with each backend: Chez locks it for ever, so each call that passes
    one keeps some memory; Racket keeps nothing after the call; RefC passes
    the closure, not a C function pointer.  A callback is only called by the
    thread that runs the Idris code.  The Readline sample no longer says that
    Idris frees the string that a foreign function returns.

### Compiler changes

* The casts of integer literals to `Double` are folded when the `Double` is
  exact (up to 2^53): `x < 0` at the type `Double` in a `let` without a type,
  where the elaborator leaves `fromInteger 0`, converted an `Integer` at run
  time (an update of an array of records with such literals runs 15% fewer
  instructions with RefC).

* In `%foreign`, `%foreign_impl` and `%export`, a string literal may be
  followed by more specifiers on the same line: `%foreign "scheme:f" (lib
  "f")` has two specifiers, and so has `%foreign "scheme:f" lib "f"`.  Both
  used to be an application of the string, which never type checked.  Other
  expressions are applied as before (`%foreign lib "f"` is one specifier, and
  `%foreign (lib "f") (lib "g")` is still an application), so no declaration
  that compiled before changes its meaning.  The test
  `idris2/misc/foreignSpecs001` has the forms.
* RefC is the default code generator of `idris2` itself, not only of the
  build: `-o`, `:c` and `:exec` compile via C unless another one is chosen
  with `--cg`, `IDRIS2_CG` or `:set cg` (for instance `--cg chez`).
* `idris2` exits with code 1 when the file it is given can't be read (with
  `--check`, `-o` or `--exec`), when the expression of `--exec` or the
  command of `--client` fails, and when `-o` or `--exec` can't compile: it
  used to exit with 0 then.  `--exec` no longer goes on to run the
  expression when the file can't be read.
* `idris2 --build` exits with code 1 when the executable of the package
  can't be compiled (the C compiler fails, for instance): it printed the
  errors and exited with 0
  ([#3767](https://github.com/idris-lang/Idris2/issues/3767)).  It says
  `Error: Compiling the executable <name> failed` and does not run the
  `postbuild` script then, and `--install`, `--install-with-src` and
  `--repl` stop there too instead of going on after the failed build.
* `idris2 --exec` exits with the exit code of the program it runs (it
  always exited with 0 when the program ran, whatever its exit code), and
  `:exec` at the REPL says when the program exits with a code other than 0
  (`The program exited with code 3`).  A program killed by a signal gives
  128 + the number of the signal, as shells report it.  For a backend built
  with the compiler API, `executeExpr` of `Codegen` returns the exit code of
  the program (`Core Int` instead of `Core ()`).
* The inlining heuristic also inlines small public definitions that are not
  just a call (up to 12 nodes: nested primitive operations, calls and cases),
  such as `==`, `div` and `mod` on `Int`, and constant folding folds `Int`
  operations, and casts to `Int`, whose arguments and result fit in 32 bits
  (the same on every back end).  A loop over `Int` doing `mod`, `div` and
  `==` runs 2.5 times faster with the RefC backend.
* The inlining heuristic does not inline every function of a group of small
  mutually recursive functions (such as `forget` on `Odd` and on `Even` in
  `Data.List.Alternating`): each round of inlining unrolled their recursion
  further, in their module and again in every module using them, and a small
  program using `Data.List.Alternating` took ten minutes to compile.
* The `case` blocks of a function with `%spec` arguments (including those
  of `if` and of `!` notation) are specialised by these arguments too, when
  they are in scope: a specialised copy of the function used to call the
  generic block, which still took the arguments at run time.  A specialised
  copy cannot refer to the names of modules that are not imported where it
  is made, though; it then calls the generic code.
* So are the `case` blocks with a wildcard alternative (`_ => ...`): the
  copy of such a block did not elaborate (the `_` is a pattern variable with
  a machine name), so a specialised copy of `mergeBy` compared two elements
  and then called the generic function, which applied the closure.
* Two blocks of a function no longer get the same specialised copy when they
  are specialised by the same arguments: their names hashed the same (the
  hash left out their index), so the copy of one block ran for the other.
* Nor do the calls of a `%spec` function by different arguments whose hash
  was the same: the hash that names the copies multiplied by 33 and added,
  so that the names `Ab` and `BA` hashed alike, and `pick BA` ran the copy
  made for `pick Ab`.  The copies are named by a hash that mixes better, and
  a copy records the arguments that it was made by (in the TTC file): it is
  only reused for them, and the next hash names a copy by other arguments.
* The copies are named in the namespace of the module that makes them
  (`_PE.M.PE_f_...`, made in `M`), so that two modules that do not import
  each other never make two copies of one name: when the hashes of their
  arguments were the same, a module importing both called one copy for
  both.  A module reuses the copies that the modules it imports made by the
  same arguments, as before, also when the arguments name copies that two
  modules made alike (`total2` at a copy of `Sz (List Int)` made in each,
  by --spec-interfaces).  The hidden option `--debug-spec-collide`
  gives all the copies of a function the same hash, for testing.
  A copy that is not used (one that calls itself, or misses cases) is no
  longer reused by the modules that import the module that made it.
* No copy is made of a `%spec` function that matches on a static argument
  where it cannot be reduced (an `export` function of another module): the
  copy called itself with the same arguments, so that a `total` program
  looped forever, or got a wrong result where the copy was taken for the
  identity.
* A specialised copy made by `%spec` is no longer checked against the default
  totality of the module where it is made (neither was one made by
  `--spec-interfaces`).  The copy runs the code of the implementations it is
  given, which calls what the methods hide from the totality checker: a
  `total` function calling `lookup` of `Data.HashMap` with a `Hashable`
  whose `hashWithSalt` used `mod` was reported not covering, because its
  copy called `prim__mod_Int`.  A copy is as covering as its function and
  the names in its arguments; one that misses cases that its function does
  not miss is not used.
* Specialising by `%spec` no longer overflows the stack of the compiler, or
  runs forever, when a static argument is a call of a function that does not
  terminate (`f (loop 0)`), when the body of the copy does not terminate (`f
  loop` where `f` calls its argument, or a function that calls itself with a
  bigger static argument, `count x y = if y == 0 then x else count (S x) y`),
  or when a recursive call that cannot be reduced makes a copy by a static
  argument that grows (`g x (S y) = g (S x) y`: a copy for every `x`), or
  when the copy builds an infinite structure (`index n (iterate f 0)` ran
  out of memory).  Nor does it take long on a static argument that is total
  but huge (`f (length (replicate 300000 ()))` took 31 s and 900 MB).
  Normalising a static argument, and reducing a clause of a copy, take at
  most 100,000 steps (a step is the unfolding of a definition, or an
  argument of the result that is quoted), and at most ten copies of a
  function are made one in another; past that, no copy is made and the
  function is called as it is (`--log specialise:3` and `--log
  specialise.fail:1` say so, `--log specialise.steps:10` shows how many
  steps each reduction takes).
* `%spec` on a name that is not the name of an argument of the function is an
  error: it was ignored (in `f : (a -> a -> Ordering) -> ...`, the argument
  has no name).
* New option `--spec-interfaces` (experimental): the small or recursive
  functions that take implementations of interfaces are specialised by them
  where they are known, as if declared `%spec` on them, so that their copies
  call the methods directly instead of applying the closures of a dictionary
  (a tree sort of `Integer`s runs with 38% fewer instructions with the RefC
  backend).  Its copies only reduce the implementations and the methods of
  interfaces, once.  `--log specialise.auto:10` shows what it specialises.
* `--spec-interfaces` costs much less compile time.  Making the run time
  definitions of a function made them again for every copy that they made
  (for `%spec` too, which makes few copies).  It makes no copy where nothing
  is gained at run time: in a type or an argument of quantity 0, of a
  function that computes a type or a proof (`=`, `Void`), or by an
  implementation of an interface of proofs (`Uninhabited`, `Injective`).  An
  argument that it specialises by is at most 200 nodes big (the types in
  proofs can be huge), a clause of a copy at most 5000 after reduction, and
  at most 16 copies are made one in another, 4 of them of one function (the
  polymorphic recursion of a finger tree made a copy for every depth of the
  type).  Checking the whole
  compiler with it takes 1.1 times the instructions of checking it without
  (5.8 times before), `Core.Termination.SizeChange`, the worst module, 3
  times (350 times), and building the libraries 1.07 times (1.9 times, with
  1.8 GB of memory for contrib's `Data.Nat.Factor`).  The copies that the
  benchmarks run are the same.
* The copies made by `%spec` and `--spec-interfaces` add nothing to the IDE
  metadata: their names (`PE_...`, `_pe...`) were highlighted at the
  locations of the calls.
* A local function whose pattern variable has the name of one of its
  parent's (`xs` in `show'` of `Show (List a)`) can be specialised: its copy
  did not elaborate ("Non linear pattern variable"), and the generic function
  was called.
* The specialised copy of a recursive `%spec` function calls itself where
  its case blocks or local functions recurse: the local functions of a
  `%spec` function are specialised by its `%spec` arguments too, as its
  case blocks are, and both by the pattern variables that are these
  arguments, not by the names of the arguments in its type (`insertAt` of
  `Data.HashMap` binds `k`, the name of its type argument, to the key, so
  its case blocks were specialised by the key, which is never known, and
  its copy called the generic function).  Lookups and deletions in a hash
  map take 7% to 8% fewer instructions with the RefC backend.
* With `--spec-interfaces`, a recursive function is copied once by an
  implementation: the recursive call in the copy took the implementation
  reduced a bit more each time, and made another copy (four copies of
  `toTree` of the treeInt benchmark, one in another).  Checking the
  compiler with the option takes 2.4% fewer instructions, and its TTC files
  are 3.8% smaller.
* RefC: a call in tail position that passes an erased argument to a
  borrowed parameter is a tail call (a specialised copy that calls itself
  recursed on the C stack).

* An "Undefined name" error suggests the modules that export a definition of
  that name, when they are not imported (for example `Data.List` for
  `sortBy`).  The modules searched are those in the build directory and in the
  packages in use.  Modules that are already imported are not suggested (the
  name is then hidden, or needs another qualifier), and for a qualified name
  only the modules with a matching namespace are.  What these suggestions read
  of the TTC files is kept for the session (also across reloads in the REPL
  and IDE mode) while the files do not change, instead of reading and decoding
  every TTC file of the packages in use for each undefined name.  The list of
  the TTC files of each directory is kept too, while none of its directories
  changes (so a module built later in the session is found), instead of
  walking the directories and parsing the path of every file for each
  undefined name.  Checking a file importing modules of `base` and `contrib`
  takes 1.8 G instructions instead of 3.5 G with five undefined names, and
  2.7 G instead of 12.6 G with thirty.
* The "Did you mean" suggestions for an undefined name are much cheaper to
  find, with the same suggestions in the same order: the name was compared to
  every name in the context with a full edit distance (allocating a matrix for
  each), which took most of the time of checking a file with a few typos.
  Names whose length differs too much are now skipped without computing their
  distance, and the computation stops as soon as the distance is known to be
  too large.  Checking a file importing modules of `base` and `contrib` with
  five undefined names takes 4.7 G instructions instead of 25 G (one undefined
  name: 2.7 G instead of 7.5 G).
* A `total` function that uses an implementation of an interface with a
  method that is not covering is no longer total.  `div` and `mod` of
  `Integral` are declared `partial`, and the implementations for the
  primitive integer types and `Nat` do not define them for a zero divisor,
  yet ``f x y = x `div` y`` was accepted in `%default total` code: the call
  goes through the method's projection, which is covering, and the record
  of the implementation was checked for coverage before its methods were
  defined.  The error names the implementation and its methods: "`f` is not
  covering.  Calls non covering function Prelude.Num.Integral implementation
  at ...", followed by "Prelude.Num.Integral implementation at ... is not
  covering, because of Prelude.Num.div, Prelude.Num.mod".  When the
  implementation is a constraint argument (`Integral a => ...`), the
  function is total relative to it, and the function that chooses the
  implementation is checked.  The check is per method: only an
  implementation of which the function may use a method that is not
  covering counts, so the ranges of `Int` and `Integer` (`[x .. y]`, which
  pass `Integral Int` on to the `Range` implementation but use none of its
  methods), `+` through the `Num` parent of `Integral`, and the covering
  methods of an implementation are total.  What a function may use of an
  implementation is found by following it through matches, constructors
  (constraint tuples, implementations built from others) and the functions
  it is given to, in this module or others; anything else (applying it,
  `let`, returning it, a function whose definition is unknown) uses all of
  it.  Default methods, and methods using other methods of their
  implementation, count as not covering when those are not.  Write
  `assert_total` where the divisor is evidently not zero, or make the
  function `covering` or `partial`.  Covering functions
  are not affected by default; with the new `--method-totality` flag they
  are checked the same way.  Whatever the flag, what makes an
  implementation, or a function using one, not covering this way is
  recorded in the TTC, so the check sees through modules checked without
  the flag.  (The non-termination of a method was already accounted for.)
  `prim__div_Double`, and so `/` on `Double`, is now total: dividing a
  `Double` by zero gives an infinity or NaN on every backend.  The TTC
  version changes.
* A function that matches on a type is no longer total when it takes out of
  the type, and uses, a variable that can hold a function over types: with
  `data I : (Type -> Bool) -> Type`, the clause `J (I f) = f` makes `J` an
  inverse of `I`, which embeds `Type -> Bool` in `Type` and let
  `%default total` code prove `Void` (#1326, #1116).  The variable must have
  type `Type`, a small type (no `Type` in it, no type variable, no data type
  that stores a type) or be a family from a small type to `Type`; this also
  covers the codomain that a pattern `(a -> b)` binds as a function from `a`,
  and `case` and `with` blocks.  Variables that are bound but not used, and
  types that a clause mentions without matching on them, are not affected.
  The error reads "`J` is not total, since matching on a type gives it `f`,
  which can hold a function over types".  The TTC version changes.
* The strict positivity check no longer accepts data types that hide a
  negative occurrence of themselves, which let `%default total` code prove
  `Void`:
  - in a parameter of another data type that uses its parameter negatively
    (`MkBad : Neg Bad -> Bad` with `MkNeg : (a -> Void) -> Neg a`); a
    parameter is now positive only if the constructors of its type use it
    strictly positively and it does not also appear in an index of their
    return type, so `(D = e) -> (e -> Void) -> D` is rejected too (#1988);
  - in a type-level lambda, such as the second argument of a dependent pair
    (`MkBad : (n : Nat ** (Bad -> Void)) -> Bad`).
  A type-level function applied to the type is now accepted when every clause
  of the function matches that argument with a variable and uses it strictly
  positively (`Arr d r` with `Arr` defined by matching on `d`; also #2297),
  where it used to be either rejected outright or, when passed through a
  parameter, accepted without looking.
  The positivity of the parameters of each type constructor is recorded in
  the TTC of its module (as a flag), so that a module that imports it needs
  neither its constructors nor the types they mention: a module does not
  load the modules that its imports import privately, and the check failed
  on their types ("Data.IOArray.IOArray not a data type" for
  `data Rose = Node Int (IArray Rose)` in a module that imports only
  `Data.Linear.Array`).  A type with no constructors, such as the external
  `ArrayData`, uses its parameters strictly positively.
* A totality error that comes from a path of calls ("possibly not
  terminating due to recursive path ...", or "due to function ... being
  reachable via ...") lists the calls of the path with their locations, under
  "Calls on the recursive path:" or "Calls leading to the non-terminating
  function:", instead of only pointing at the declaration of the function.
* When interface search finds an implementation that matches the goal but
  cannot find one of the implementations that it needs in turn (usually a
  constraint of that implementation), the "Can't find an implementation"

* Added the `--error-format <human|json>` command line flag. With
  `--error-format json`, errors and warnings in batch mode (`--check`,
  `--build`, `--typecheck`, `--client`) are printed on stdout as one JSON object
  per line, with fields `severity`, `file`, `start`/`end` (1-based `line` and
  `col`, omitted when there is no location) and `message` (plain text, without
  the source excerpt). Informational output such as the "Building" progress
  lines goes to stderr instead. The default is `human`.
* Added the `-Wwhere-recompute` (or `--warn-where-recompute`) flag, which
  warns about local (`where` or `let` block) definitions without arguments of
  their own that use variables of the enclosing definition and are used
  repeatedly. Such definitions are lifted to functions of those variables, so
  they are recomputed at each use rather than shared like a `let` binding.
  The warning is off by default.
* The REPL has a built-in line editor when it runs in a terminal: readline
  key bindings (cursor movement by character and word, kill and yank, history
  search with the arrow keys), a history kept between sessions in
  `~/.idris2_history` (see `IDRIS2_HISTORY_FILE`), and syntax highlighting of
  the line as it is typed (`:command`s, keywords, literals, comments, holes and
  capitalised names), which follows the `--color` setting.  It is written for
  the Idris2 compiler itself (no `readline` library needed), works with all
  back ends, and is not used when the input or output is not a terminal; set
  `IDRIS2_LINE_EDITING=0` to turn it off (for instance under `rlwrap`).
  `Tab` completes the names of commands, pragmas and names in scope (also in
  the arguments of commands such as `:t`), listing the candidates when the
  word can't be completed further.
  The editor places the cursor by the columns that characters take up on the
  terminal (two for CJK characters and most emoji, none for combining
  marks), also when the line wraps, and the cursor keys, `Backspace` and
  `Delete` go over a character together with the combining marks after it.
* The constant folding of the shifts, negations, `div` and `mod` of the
  fixed width types is computed on `Integer`s (then wrapped around) instead
  of with the primitives of the backend that built the compiler, so that the
  folded constants are what the program computes at run time on every
  backend (`ash` semantics: a shift by the width or more gives 0 or -1, a
  negative count shifts the other way), whichever runtime the compiler runs
  on.  A compiler built on an older runtime folded `prim__shl_Bits32 1 32`
  to 1, and the smallest value `div` -1 trapped in C.  Shifts of `Integer`s
  by more than 4096 are left to the run time.
* Giving the local variables of a definition their names for the code
  generators ("Forget names" in `--timing`) takes time about linear in the
  depth of the code, instead of cubic when the same name is bound again and
  again (as in a long chain of inlined binds): 8,800 nested `let`s took 7
  minutes.
* The names that the elaborator makes for nested (`where`) functions, case
  and with blocks and metavariables are in the namespace of the module, not
  in the current namespace.  They are numbered by a counter of the module,
  and the current namespace can be that of another module (in the module
  `A`, the block `namespace B` has the namespace `A.B`, which is also that of
  the module `A.B`): two modules could make the same name, and in a program
  importing both, one definition silently replaced the other (a `where`
  function or a with block of one module ran the code of the other).  The
  TTC format version changes accordingly.
* Building the size change graphs for the totality checker no longer takes
  time exponential in the length of a chain of `let`s which each use the
  previous variable twice (`let x2 = f x1 x1 in let x3 = f x2 x2 in ...`):
  substituting the values of the lets made the right hand side exponentially
  big; 16 such lets took 0.7 seconds and 50 ran out of memory.  When
  substituting them would make the term more than 16 times bigger (and
  bigger than 10,000 nodes), the lets stay, and an argument is then only
  seen to be smaller through a let bound variable given directly as the
  argument.  Otherwise nothing changes.
* Parsing no longer takes time exponential in the depth of nested
  parentheses: each parenthesised expression was parsed twice, first as the
  binder of an operator (`(x : a) ** b`, `(x <- e) >>= k`), so a sum of 12
  nested parenthesised terms took 2 seconds to parse, and each level more
  twice as long.  A binder is now only tried when there is a `:` or a `<-`
  directly inside the parentheses.
* Elaborating deeply nested binders is faster: 400 nested `let`s took 13
  seconds to check and now take 0.7, and a `do` block of 400 binds 44
  seconds instead of 8 (it is still about cubic: each search for an
  implementation tries every variable in scope).  The metadata for the IDE
  substituted the variables in scope one at a time, solving a metavariable
  normalised the types of all the variables in scope, and unifying an
  application of a metavariable evaluated the types of all its arguments
  instead of only the last one.
* The inliner ("Compile defs" in `--timing`) no longer closes each binder it
  makes over its scope with a pass over the scope: a chain of 512 inlined
  binds is inlined in 3.6 s instead of 65 s, 1,024 binds in 19 s instead of
  380 s.  The code it makes is the same.
* The inliner does not inline a function into its own body.  Inlinable
  functions that call each other (such as the copies that `%spec` makes of
  the case blocks of a recursive function) got their recursion unrolled
  again in every round of transformations: the copy of `nextDirEntry` in the
  compiler (System.Directory, `%spec hio`) had it unrolled 133 times, 15,000
  lines of C nested 266 levels deep, now 530 lines.
* Reading and putting together paths (`parse`, `</>`, `<.>`, `<..>`,
  `joinPath` and cleaning a path, in `Libraries.Utils.Path`) no longer runs
  the lexer and parser of paths on plain POSIX paths (names separated by
  single `/`, after an optional root or `./`, with no `.` or `..` and no `\`,
  `:` or `?`): they are read or put together as strings, which gives the
  same result.  Looking for the TTC file of an import in each search
  directory parsed several long paths, which was a third of the work of
  checking a small file importing three modules of `contrib`, and more of a
  no-op `--build`.  Other paths, and all paths on Windows, still go through
  the parser.
* Checking modules takes 7% to 38% fewer instructions (libs/base: 11%,
  modules of the compiler: 12% to 38%), from a profile of the type checker:
  sorting the implicit bindings of a clause compared the metavariables of
  every binding again at every step, and the case builder made an
  environment as long as the scope for every pattern; proof search looked up
  the full name of every hint (decoding its definition) to check that it was
  not hidden, also when nothing was; checking that a name is visible
  reversed lists of identifiers for every visible namespace; the interval
  maps of the metadata for the IDE compared positions through the instances
  of pairs, and were rebuilt element by element when read or written; the
  position in a TTC buffer was an `Integer`; and a module imported a second
  time had each of its definitions decoded again.  The TTC and `.ttm` files
  are the same as before.
* Bringing the imports of a module into scope costs less:
  + A process that checks several modules (a build without `--jobs`, the
    REPL, the IDE mode) keeps what it read of each TTC file for the next
    modules that import it, instead of reading and decoding the file again
    for each of them (the definitions are still decoded only when they are
    used).  A file is read again once it has changed (its size or times
    differ).  The files kept are at most 32 MB, or as many megabytes as the
    new environment variable `IDRIS2_TTC_CACHE_MB` says (`0` keeps none).
  + `--check` no longer reads the checked module again, with everything it
    imports transitively, once it is built: that is for the REPL, and for
    `--exec`, `-o` and `--client`, which still do it.
  + The fixities that each imported TTC file has (all those of its own
    imports) are only added when they are not there already, and the
    documentation of the modules read so far is no longer copied for each
    import.

  `--typecheck` of libs/base in one process takes 6% fewer instructions,
  of the whole compiler 4.5% fewer (with a peak memory 8% to 13% higher);
  `--check` of a module takes 6% to 21% fewer (Idris.REPL of the compiler:
  21%, Data.Nat.Factor of contrib: 13%).  The TTC and `.ttm` files are the
  same as before.
* A `%transform` rule now also matches an application whose implicit
  arguments are solved holes, as in `runState s (traverse f xs)` (where the
  applicative of `traverse` is found from the type of `runState`): no rule
  for a particular monad (those of the library for `IO` and `State`)
  applied there, as the rule that makes a method call a call of its
  implementation took it first.
* `%transform` rules: the right-hand side of a rule may contain binders (a
  lambda, a section, or a function type in an implicit argument, as in
  `[| f x ::: g xs |]`), which made the rule fail to apply; holes in it that
  were solved late (the implicit arguments of `map` in `map sequence (f
  xs)`) are replaced by their solutions, instead of staying holes that the
  modules using the rule did not know ("Linearity checking failed on
  metavar"); and the rules of a module are tried in the same order when it
  is imported as within it (the last first): when read from a TTC they were
  tried the other way round, so the rule that an implementation adds for its
  methods took the place of a later rule on the same method (`traverse` on a
  `List1` in `IO`).
* A function in `IO` whose body gives its action without a bind first (`loop
  acc n = if n == 0 then pure acc else loop (acc + n) (n - 1)`, a `let` or a
  case before the action, a `where` helper, a `PrimIO` action) is given the
  world as a parameter, which is pushed into the body (into the alternatives
  of a case, the scope of a let, the end of a call), instead of returning a
  closure waiting for the world.  This is done when what the body computes
  before its action is cheap (primitive operations on numbers, constructors,
  closures, partial applications, and cases and lets of these), so that an
  action made once and run many times (`let act = f x in act >> act`)
  computes again only such operations: `f x = let y = expensive x in pure y`
  keeps its closure.  The arguments of a partial application of such a
  function that are not cheap are computed once, outside the lambda that the
  application is made into.  On every back end; with RefC, the worker of such
  a function gives its result as a C integer.  A loop in `IO` that calls an
  `IO` step whose body is an `if` runs 5.4 times fewer instructions with RefC
  (9% fewer with Chez), a loop over an `IOArray` through such helpers 33%
  fewer (19% with Chez); the programs of `benchmark/` run the same
  instructions.  `--typecheck` of libs/base takes 0.09% more instructions
  (the pass), and the compiler compiled by itself is as fast and as large as
  when it is compiled without the pass.  See `Compiler.Opts.EtaIO`; the tests
  `allbackends/ioeta001` (sharing) and `refc/ioeta001`.
* The compiled definition of a data constructor has a table of its fields
  (`fields` of `MkCon`, `MkNmCon`, `MkLCon` and `MkACon`, a `FieldRep` each):
  `FPrim t` when the declared type of the field says that it always holds a
  value of the fixed width primitive type `t` at run time (a field of type
  `Double`, `Int`, `Bits8`, ..., `Char`, of an enumeration such as `Bool`, or
  of a newtype of one of these), `FBoxed` otherwise.  It is computed once,
  where the data type is declared (see `Core.FieldRep`), saved in the TTC file
  (a `ConFields` flag of the constructor, which `:di` shows), and shown by
  `--dumpcases`, `--dumplifted` and `--dumpanf`.  No back end uses it yet:
  it is the groundwork of unboxed fields in the RefC back end (see
  `docs/source/backends/refc-flat-layout.rst`), and the code generated by
  every back end is unchanged.  A back end outside this repository that
  matches on these constructors has one more argument to match.  The test
  `codegen/fieldrep001` pins the table of a set of types.
* The constructors of a list or option shaped type (or of a record of two
  fields) are no longer compiled to the intrinsic constructors
  (`_builtin.CONS`, `_builtin.JUST`, ...) when one of them has a field of type
  `Double`, `Int`, `Int64` or `Bits64` (a field that a back end may store
  unboxed): they get the flag `NoIntrinsic` and keep their names and tags
  (and their `ConInfo`, so the Scheme and JavaScript code is the same).  A
  conversion between such a type and `List`, `Maybe` or a pair is therefore
  no longer compiled away as the identity, and CSE no longer shares their
  applications with those of other types.  This hits 6 types of the
  libraries and 7 of the compiler; type checking `libs/prelude` takes the
  same instructions.  See the test `codegen/intrinsic001` and
  `docs/source/backends/refc-flat-layout.rst`.

### Building/Packaging changes

* `idris2 --dump-api pkg.ipkg` builds a package and prints its public API in a
  stable text form, one declaration per line, meant to be compared with
  `diff`: per module, the public imports, the exported fixities, every
  exported name with its visibility, totality requirement and elaborated type
  (implicits and quantities shown, names in full), the constructors of public
  data types, record fields, interfaces with their methods, and
  implementations.  It does not depend on source positions, paths, build order
  or machine generated names.  The API of `prelude`, `base` and `contrib` is committed in
  `libs/api`: `make api-check` (and the test `idris2/mkdoc/apidump002-libs`)
  fails with the difference when it changes, `make api-snapshots` writes it
  again.  See "Detecting changes to the API of a package" in the package
  documentation.

* TTC files record the version of the compiler that wrote them, and a module
  whose TTC was written by another version is rebuilt.  A TTC holds choices
  made by its compiler (inlining flags, specialised copies of functions), so
  reusing it could give a different result from building with this compiler.
  The TTC format version changes accordingly.

* `--jobs N` (`-j N`, or `IDRIS2_BUILD_JOBS`) builds the modules of a package
  with up to `N` processes in parallel, each module once the modules it imports
  are built.  `make` builds the compiler and the libraries this way
  (`IDRIS2_JOBS`, the number of processors up to 16 by default): checking the
  compiler with a RefC-built compiler takes 2m20s instead of 7m, and `base`
  20s instead of 70s, on 16 cores.  The TTC files are the same.
* Finding out that the modules of a package are up to date takes much less
  work: the header of each source file is read once (it was read again for
  each module of the package that imports it, directly or not), only the
  start of a TTC file is read for its version and hashes, and the paths of
  the TTC files of the imports are made only as they are tried.
  `idris2 --build base.ipkg` with nothing to do takes 2.3 billion
  instructions instead of 23.7 billion (0.3s instead of 2.6s), and
  `idris2 --typecheck idris2.ipkg` 10.4 billion instead of 42.5 billion (1.2s
  instead of 4.6s).
* A module that is up to date costs less again in a build:
  - The context is no longer reset (with the primitives added again) for
    each module of the build, but only before a module is built, and after
    the last one.
  - The TTC file of a module records the imports of its header, with a hash
    of the content of its source file, and they are read from there while the
    source file has the same content, instead of lexing and parsing its
    header.  The TTC format version changes accordingly.
  - The lexer makes its rules once, instead of again for each token (they
    were lazy, and lazy values are not shared), and no longer puts the rest
    of a file back together into a string after the header of a module.
  With nothing to do, `idris2 --build base.ipkg` takes 0.3 billion
  instructions instead of 4.0 billion, `idris2 --build contrib.ipkg` 0.24
  billion instead of 3.2 billion (0.19 billion instead of 1.1 billion with
  `--jobs`), and `idris2 --typecheck idris2.ipkg` 0.75 billion instead of 14.2
  billion.
* `make help` lists the targets of the top-level `Makefile` and the variables
  that change the build, with their current values.
* `make` rebuilds the support libraries (`support/c`, `support/refc`) whenever
  their sources or headers changed, including the RefC runtime library, and
  `make test` reinstalls them in `build/env`.  They could be left stale before.
* With the RefC backend, a plain `make` now compiles the C of the compiler with
  `-O1` and without link time optimisation, which is quick to build.
  `make LTO=1` (see `config.mk`) uses `-O2 -flto=auto` when the C compiler has
  it: the compiler is about 4% faster, and its C takes about twice as long to
  build.  `make bootstrap-c` still builds the compiler that it leaves for
  installing with `LTO=1`, unless it is run as `make bootstrap-c LTO=0`; the
  first compiler of that bootstrap, which only builds the libraries and the
  second one, is compiled with `-O1` and without LTO (`BOOT_CFLAGS` changes
  this).  An `IDRIS2_CFLAGS` or `CFLAGS` from the user still takes precedence.
* The RefC backend generates the C of a big program faster: it cut the
  program in units with the `div` of `Nat`, which counts down in unary (as
  many steps as the size of the C in bytes); the C of the compiler takes 6.8%
  fewer instructions to generate.
* With the RefC backend, `make` builds the libraries that do not depend on each
  other at the same time (`contrib` and `linear`, then `test`, `papers` and
  `network`), dividing `IDRIS2_JOBS` between them; `LIBS_PARALLEL=1` builds them
  one after the other, which is always the case with the Scheme backends.  The
  dependencies between the libraries in the `Makefile` now follow what they
  import (`network`, `test` and `papers` were missing `base`).
* `make` no longer rewrites `src/IdrisPaths.idr` when its content is the same,
  so a second `make` does not rebuild the modules that import it.
* `idris2 --build` no longer compiles the executable of a package again when
  it is certainly up to date: it prints `The executable ... is up to date, not
  compiling it again` instead of `Now compiling the executable`.  Compiling an
  executable is a whole-program compilation, as slow when nothing changed
  (about 90s for the compiler itself) as after a change.  After it succeeds,
  a stamp file (`build/exec/<executable>.stamp`) records the settings of the
  compilation (the main module, code generator and directives, options,
  directories, the `IDRIS2_CC`/`CFLAGS`/... variables of RefC and those that
  the C compiler reads, such as `CPATH`) and the state (modification time
  and size) of what the executable is made from: the TTC files of the program,
  of its dependencies too, the compiler, the runtime support files and
  libraries (also those in the `-L` directories of `IDRIS2_LDFLAGS` and in
  `LIBRARY_PATH`), the C compiler or Scheme, the C headers of `%foreign`s
  that are not those of the runtime and the headers they include (as the C
  compiler finds them), and the executable itself.  The
  executable is compiled again unless all of that is as the stamp says (a
  module that was built has a new TTC file).  This is done for the RefC and Chez backends, for builds
  that are not incremental, and where the compiler can tell what it is
  (Linux, or an absolute path of the compiler on the command line).
  `--clean` removes the stamp, `--log package.stamp:5` tells why a build did
  not skip the compilation.  When RefC's executable is moved to
  `idris2_app/idris2` and a launcher put in its place (as `make` does for the
  compiler), it is the moved binary that is checked.
* A module of a package is now built as if it were built alone: the
  `%language` extensions, `%foreign_impl`s and builtin names (`%pair`,
  `%rewrite`, literal names) that the modules built before it in the same
  process set are forgotten, as in the REPL.  A module that relied on them
  must set or import them itself.

* Fix parsing of capitalised package names containing hyphens.
* Change `flake.nix` to point at `idris-community/idris2-mode` as the URL for
  `inputs.idris-emacs-src` (from the user fork `redfish64/idris2-mode`).
* Fix UTF-8 character handling in package description fields.
* A project's data directory can now be specified with the `datadir` entry in
  an `ipkg` file.
* Fix building on Windows with MSYS.
* Idris 2 can now be bootstrapped with only a C compiler: `make bootstrap-c`
  builds the compiler from the C code that the RefC backend generated for it
  (`bootstrap/idris2_app/idris2.c.xz`), then rebuilds it with the RefC
  backend.  `bootstrap/update-c-bootstrap.sh` regenerates that file.
  The generated C is compiled in parallel (see below), so that compiling it
  takes seconds instead of minutes.
* `make bootstrap-c` stops with an error when `xz` is missing or cannot
  decompress `bootstrap/idris2_app/idris2.c.xz`.  It used to go on with an
  empty or truncated C file, and fail later with an unrelated error.
* The dependency files of the support libraries have a rule for each header
  (`-MP`), so that removing or renaming a header no longer breaks the build of
  `support/` until `make cleandep`.
* On FreeBSD, the include directory of the packages (for GMP) is in
  `CPPFLAGS` instead of `CFLAGS`, so that the dependency files of the support
  libraries and `make bootstrap-c` see it.  The RefC library built for
  AddressSanitizer (`make install-support-refc-asan`) is compiled with the
  usual `CFLAGS` too (`-fPIC`, the warnings).
* `make install` after `make bootstrap SCHEME=chez` installs the libraries
  with the compiled Chez code of their modules again (for incremental builds),
  which it stopped doing when RefC became the default `IDRIS2_CG`.  The
  libraries are compiled for incremental builds with `LIBS_INC_CGS`: `chez`
  when `IDRIS2_CG` is `chez` or when the compiler in `build/exec` runs on Chez
  Scheme, and nothing otherwise (the RefC and Racket backends have no
  incremental builds, `IDRIS2_INC_CGS=refc` was ignored).  `IDRIS2_CG=chez
  make install` is no longer needed after a Chez bootstrap.
* The support files are installed with their modification times
  (`install -p`).  `make test` reinstalls them in `build/env` every time,
  which made the test runner look out of date to the executable stamp and be
  compiled again (about 10 s) on every run.
* `make bootstrap-c` compiles the C of its first compiler in 16 parts (or
  `BOOT_PARTS`), `BOOT_JOBS` at a time: the number of processors up to 16,
  and on Linux no more than one per 1.5 GB of available memory.  It used to
  make one part per processor, all at once, and the memory that the C
  compilers need together hardly depends on the number of parts (about 13 GB
  with GCC at `-O1`): on a machine with few processors and little memory,
  they could need more than it has.  `IDRIS2_CC_JOBS` of RefC defaults to the number of processors up to
  16, like `IDRIS2_JOBS`.  A library that `make` builds on its own (as in `make
  linear`, or the bootstrap libraries) uses all of `IDRIS2_JOBS` instead of
  half of them.
* The nix package (`nix build`, the default package of the flake) follows the
  switch of `make` to RefC: the compiler, built with RefC from a compiler
  bootstrapped with Chez, is `bin/idris2_app/idris2` with a wrapper that lifts
  the stack limit like the launcher of `make` does.  Its wrapper, and that of
  the Chez bootstrap package, give the compiler a C compiler (`IDRIS2_CC`,
  else `CC`, else the one of nixpkgs) and GMP (added to `IDRIS2_CPPFLAGS` and
  `IDRIS2_LDFLAGS`), which the RefC backend needs to compile programs; `CHEZ`
  is still set for `--cg chez`.  `buildIdris` installs the executable of RefC
  without its C sources and objects.

### Backend changes

#### RefC Backend

* Flat arrays, the accesses (see `docs/source/backends/refc-flat-layout.rst`,
  stage C): in a program that uses flat arrays, the functions that access
  them have the small functions on their elements inlined (the
  copies of the array functions, the `Res` they give, the functions on the
  records), an element read is its presence and its fields read as C
  numbers, a record is made from them only where it is used as a value, and
  an element written is written from its fields, without the `Just`
  (`Compiler.RefC.FlatOpt`; the accesses are those of prim.h, inline when
  the array has the layout expected and is not shared, through values
  otherwise; an element read by its fields is taken whole first, under the
  lock of a shared array, so that its fields are those of one write).  A
  variable that is the value of a `let` (in a branch of a `case` that the
  `let` binds) is a C number when the variable of the `let` is one.
  Instructions, full inputs: the particle simulation on flat linear arrays
  4.47 G (16.09 G on the linear arrays of values), the heap of events
  11.85 G (44.47 G).  The log topic `compiler.refc.flat` shows the
  definitions changed.  The tests `refc/flatopt001` and `refc/flatopt002`.
* A constant with fields stored raw (see below), whose fields are literals,
  is static data of the program, as the other constant constructors are.
* Flat arrays, the plumbing (see `docs/source/backends/refc-flat-layout.rst`,
  stage B): `Data.IOArray.Flat` (base, re-exported by `Data.IOArray`) has
  `Layout`, the interface `Flat` of the layouts of the elements of arrays,
  with a default (values) for every type and implementations for the
  primitive numbers and `Char`; the compiler makes the implementation for a
  record of one constructor whose fields are all stored raw, where it is
  declared (in a module that loads `Data.IOArray.Flat`).  `Data.IOArray` has
  `newFlatArray`, `readFlatArray` and `writeFlatArray`, which take the `Flat`
  of the elements; its other functions are unchanged, and read and write an
  array of any layout.  `Data.IOArray.Flat` has the primitives
  `prim__newSlots`, `prim__slotGet` and `prim__slotSet`, which the Scheme and
  JavaScript back ends compile as the other array primitives.  In a
  program that uses them (they are on exactly then: a program that does not
  is compiled as before, the same C; `--directive refc-no-flat-arrays` turns
  them off), RefC stores the elements of such an array inline (a word for the empty slots, then the primitive or
  the raw fields of the record), and the functions that take a constant
  layout get copies with inline accesses (`Compiler.RefC.FlatClones`).  The
  tests `allbackends/flatarray001` and `refc/flatarray001`.
* The fields of a constructor whose type says that they always hold a
  `Double`, an `Int`, an `Int64` or a `Bits64` are stored in its cell as C
  numbers, after the fields that are values (`total` counts these only, so
  the runtime never looks at the others): a record of four `Double` and an
  `Int` is one cell of 48 bytes instead of a cell and four boxes.  A field
  matched is a C number (a variable that the unboxing keeps in a C `double`
  or `int64_t`), a constructor is built from C numbers, a cell taken over by
  a constructor of the same layout keeps the raw fields that do not change,
  and the copy made when it is shared copies them as they are.  Instructions:
  a particle simulation on an array of records 2.09 times fewer, an n-body
  simulation 3.1, a Mandelbrot set on records of two `Double` 5.0, a heap of
  records of `Int` 1.08, lists and trees of `Int` 1.07; the five programs of
  `benchmark/` the same; the compiler compiled by itself type checks
  `libs/prelude` in 1.6% fewer instructions, and its C compiles in the same
  time.  `--directive refc-no-raw-fields` turns it off;
  `--directive refc-check-layout` makes every match test the number of
  pointer fields of the cell (after a `believe_me` between types laid out
  differently, which is undefined behaviour).  Code that reads such a cell in
  C uses `idris2_rawField`.  The tests `refc/rawfields001` and
  `refc/rawfields002`; the design in `docs/source/backends/refc-flat-layout.rst`.
* The values that do not come from the pools (larger than 256 bytes, or all
  of them under Valgrind or with `IDRIS2_REFC_NO_POOLS`) are aligned on 8
  bytes on 32 bit platforms too (they were aligned on the size of a pointer),
  as the cells of the pools are, for the unboxed fields of constructors to
  come.  The test `refc/rawcells001` checks the runtime (release, marking of
  shared values, the leak check, static values, reuse of cells) with cells
  that have unboxed fields after their pointer fields, as a 32 bit program
  too where a 32 bit C compiler and GMP are installed.
* A branch of a `case` that matches several cells of the same constructor
  keeps them all for the constructors that it builds, used in order, and
  releases those that no constructor takes over (it kept the first one only,
  and freed the others): the merge of two lists takes over both cons cells,
  and a function that returns a pair with a list takes over the cell of the
  pair as well.  `--directive refc-no-multi-reuse` keeps one cell of each
  constructor, as before.

* The cell that a constructor takes over is the matched value itself when it
  is unique, and otherwise a new cell with references to the fields that are
  used, made in the unlikely branch of the uniqueness test, so that the code
  that follows has no test of its own: the fields are loaded after the test,
  and the constructor does not store again a field that it leaves where it
  was (the same variable in the same field), which only `refc-size-reuse`
  did.  A branch that matches a cell when it keeps another one already for
  its constructor no longer drops the one kept for the new one.  The shared
  case of the release of a value that is not used any more is the unlikely
  branch too.  Instructions: the tree sort of phase 0 (lists/treeB) -13%,
  treeInt -5%, mergeInt -6%, the merge sort of phase 0 (lists/mergeB) -20%.
  `--directive refc-no-reuse-copy` gives the code of before.

* In a branch of a `case` that matched a constructor without fields (a `Leaf`
  of a tree, `Nothing`, an enumeration), the value is the immortal one of the
  runtime or `NULL`: no reference to it is dropped or taken any more (the
  immortal test in line cost about 10 instructions).  The tree sort of
  phase 0 (lists/treeB) runs with 3.3% fewer instructions, treeInt 0.8%.
  Other immortal values (the closures of a dictionary that a function gets
  as an argument, most of the count operations on immortal values of
  treeInt) are not known when the code is generated.  Off with `--directive
  refc-no-static`.

* Backtraces: a program that dies of a fatal error (`idris_crash`, a missing
  case in `partial` code, a division by zero, a missing foreign function, or
  `SIGSEGV`, `SIGBUS`, `SIGFPE`, `SIGILL` or `SIGABRT` from foreign code or a
  stack overflow) can print the functions of the thread that died on stderr,
  after the message.  `--directive refc-backtrace` puts the Idris names of
  the functions and where they are defined in the program (and compiles them
  with `noinline`) and turns the backtraces on; `IDRIS2_REFC_BACKTRACE=1` or
  `0` turns them on or off when the program runs.  The stack is walked by the
  unwinder of the C compiler only when the error happens: a program runs the
  same code with or without them.  With `IDRIS2_REFC_DEMANGLE=1`, a program
  compiled with the directive replaces the C names of its functions in its
  input by their Idris names (for the output of `perf`), see "Backtraces" and
  "Profiling with perf" in the RefC documentation.  `idris_crash` is
  declared `noreturn` in the runtime, so that the C compiler does not make its
  call a jump (which hid the frame of the function that crashed).

* A program that uses `setEnv`, `unsetEnv`, `enableRawMode` or
  `resetRawMode` of `System` compiles: `idris_support.h` had no prototypes
  for their C functions, and GCC 14 refuses the implicit declarations.  The
  `%foreign` declaration of `isNull` in `Network.Socket.Data` names the header
  that declares it, `idris_net.h`.  `support/refc/check-foreign.sh` checks
  that every C function of the `%foreign` declarations of a set of Idris
  sources that RefC calls is declared in the headers that the generated C
  includes and defined by the support libraries; the test
  `refc/foreigndecl001` runs it on the libraries.

* A foreign function that returns a function (`PrimIO (Int -> Int)`) is a
  compile error, which says that the RefC backend does not support it: the
  generated C called a `makeFunction` that does not exist.

* The `Struct` type of `System.FFI` is supported (#3830): a struct can be
  passed to and returned from foreign functions (compiling a program with one
  used to stop with `INTERNAL ERROR: Struct access not implemented`), and
  `getField` and `setField` read and write its fields.  As in the Chez
  backend, the layout is that of the C `struct` that the fields of the Idris
  type describe (`Int` is `int`, the fixed width integers, `Double`, `Char`,
  `Ptr t`/`AnyPtr`, and another `Struct`, which is a pointer to a struct), and
  the generated C defines it under a name of its own, so no header is needed.
  A field of another type, two `Struct` types with the same name and
  different fields, a struct that is in the type of no `%foreign` function
  and a `getField` whose struct or field name is not known at compile time are
  compile errors.

* `System.Info.os` gives the names of the Scheme backends: `"unix"` (Linux
  and the BSDs), `"darwin"`, `"windows"` or `"unknown"`, instead of `"Linux"`,
  `"macOS"`, `"FreeBSD"` and so on.
* A program with a name that cannot be compiled (a hole, for instance) is
  compiled, like with the Scheme backends: it stops with the message when it
  gets to that name.  It used to be an internal error of the compiler.
* A crash of the compiled code itself (a case without a clause for the
  value, like `void` applied to a value) prints its message and stops with
  exit code 1, like with the Scheme backends.  It used to go on silently
  with a null value.
* `:exec` runs the compiled program also when the path of the build
  directory has spaces or other characters that the shell would take.
* The fixed width integer types give the results of the Scheme backends.
  The results of `+`, `-` and `*` on `Bits8` and `Bits16` were not wrapped
  around in the value, so that a cast to a wider type (`cast {to = Bits16}
  (x + 200)`) or a `case` on literals saw the value before the wrap; the
  casts from `Int8` to `Bits8`, from `Bits8` to `Int8` (and the other casts
  that kept the value as it was) did not convert it.  A shift by the width
  of the type or more gives 0 (or -1), instead of what the C compiler makes
  of an undefined behaviour, and a shift of a signed type (or an `Integer`)
  by a negative count goes the other way.  `negate` on the `Bits` types
  compiles.  The headers compile for 32 bit targets when `UINTPTR_WIDTH` is
  defined (C23), and the casts to `Int32` give an `Int32` there.  As the
  compiler built with RefC folds constants with these primitives, this also
  fixes the folding of such constant expressions (`prim__shl_Bits32 1 32`
  was folded to 1) for every backend.
* `idris_crash` exits with code 1, like with the Scheme backends (it was
  255).  `copyData` within one buffer copies overlapping ranges correctly
  (it used `memcpy`), and running out of memory for a buffer or an array
  stops with a message instead of crashing later.  In the C support library
  of every backend, `Network.Socket.recv` no longer writes a byte past its
  buffer when it fills it, `fGetChars` stops with a message when it runs out
  of memory, and the messages of failed assertions show their arguments.
* Functions and closures of more than 255 arguments compile (the C compiler
  rejected the arity of their closures, which was 8 bits; it is 16 bits now,
  in a closure of the same size).  The compiler reports a function of more
  than 65535 arguments, or a constructor of more than 65535 fields.
* Nested functions (`where`) of the same name in the same namespace of two
  modules (the module `A.B`, and a `namespace B` in the module `A`) could get
  the same C name, and the C compiler rejected the program.
* A definition whose name ends like that of a C function that the code
  generator makes for another one (`x_constant` for a constant `x`, `f_borrow`
  for a foreign function `f`) no longer has the C name of that function, which
  the C compiler rejected: these functions are now named `idris2_caf_...` and
  `idris2_borrow_...`.  The C names that begin with `idris2_` are the support
  library's and the code generator's: a definition whose C name would begin
  with it (one of a namespace `idris2`) is given the prefix `idris2_user_`.
* Fixed an issue to do with `alligned_alloc` not existing on older MacOS
  versions, causing builds targeting PowerPC to fail (#3662).  For these
  systems, the compiler will now use `posix_memalign`.
* Fixed integer comparison operators returning incorrect results on WASM32.
  The `idris2_extractInt` function incorrectly used `idris2_vp_to_Int32` for
  unboxed values, which dereferences unboxed pointers as `Idris2_Int32*`
  (previously `Value_Int32*`) on 32-bit platforms when `UINTPTR_WIDTH` is not
  defined (common in Emscripten).
* Fix missing support for sized, signed integers in FFI.
* Fix headers for numeric negation.
* Prefix RefC Idris values with `Idris2_` to prevent name collisions with third
  partly libraries.
* Fixed casts from `String` failing to compile
  ([#3812](https://github.com/idris-lang/Idris2/issues/3812)): the support
  library exported the cast helpers as `idris2_cast_String_to_*` while the
  generated code calls `idris2_cast_string_to_*`.
* Fix missing FFI of Data.Buffer.
* Added support for green threads: `fork` and `threadWait` from `Prelude.IO`,
  and the whole of `System.Concurrency` (mutexes, condition variables,
  semaphores, barriers, channels and thread local data) are now implemented
  in terms of green threads, i.e. user level threads scheduled by the RefC
  runtime.  Once a program forks a thread, they run in parallel on a pool of
  OS threads, one per processor (or `IDRIS2_WORKERS`; `IDRIS2_WORKERS=1` runs
  them all on the main OS thread), that take work from each other.  A thread
  that wakes another one up lets it run next on the same OS thread, so that
  message passing stays as fast as with a single OS thread.  The values that
  threads hand over to each other are reference counted atomically; the
  others are not.  A thread that runs for more than 10ms while others wait
  for its OS thread yields at the end of an iteration of a loop
  (`IDRIS2_PREEMPT=0` turns this off).  A blocking system call (such as
  reading from standard input) only blocks the OS thread that makes it;
  `sleep` and `usleep` block no OS thread, as they are implemented in terms
  of the scheduler.  Mutexes are taken and released with one atomic
  operation when no thread waits for them.  Like in the Chez backend, the
  program ends when the main expression is done.  Every forked thread runs
  on a stack of its own, 8MB by default (`IDRIS2_THREAD_STACK_SIZE` changes
  it), followed by a guard page.  Green threads are currently only supported
  on POSIX systems; on Windows and WebAssembly the backend still builds and
  runs programs, but forking a thread reports an error.
* A full application of a foreign function borrows its arguments, like a
  primitive operation: the caller no longer takes a reference to each
  argument for the wrapper of the function to release after the call.  This
  saves two atomic operations per argument that threads share (a mutex 8
  threads contend for is taken and released twice as fast), and a call
  through the trampoline in tail position.
* Fixed a memory leak of string iterators (`Data.String.Iterator` in
  `contrib`, and the lexer of the compiler): the finaliser of an iterator
  freed it but not the pointer that held it, one cell per iterator.  The
  compiler leaked 260935 of them type-checking `libs/base`.
* Fixed memory leaks of the arguments passed to the external primitives
  (`writeIORef`, `newIORef`, `newArray`, `arraySet`, `onCollect`, ...): the
  primitives take a reference to what they keep, but the caller did not
  release its own.  `modifyIORef` used to leak the previous value of the
  `IORef` on every call.
* Fixed the finaliser of a `GCPtr` / `GCAnyPtr` releasing the pointer twice.
* Fixed three races of the green threads running in parallel.  The main
  thread could evaluate its own copy of a top-level constant that another
  thread had just started to evaluate (a global `IORef` made with
  `unsafePerformIO`, say, was then another `IORef` in the main thread).  A
  thread whose timed wait (`conditionWaitTimeout`, `channelGetWithTimeout`)
  was woken up just as its deadline expired could see its next timed wait or
  sleep end at once, and the list of deadlines could be corrupted, which hung
  the program.  A deadline set just as an idle worker went to sleep could
  be missed by that worker: the thread then woke up late, once a busy worker
  was free.
* Fixed `mod` on `Int`, `Int8`, `Int16`, `Int32` and `Int64` giving the
  divisor instead of 0 for a negative multiple of it (`-4 mod 2` was 2).
* Fixed `div` and `mod` by -1 of the smallest `Int`, `Int32` or `Int64`
  crashing the program (with `SIGFPE`): the quotient wraps around, like in the
  other backends.
* `div` and `mod` on fixed-width integers are inline, so that a division by
  a constant is compiled to shifts and masks (a loop of `mod` and `div` by 2
  on `Int` runs 2.8 times faster), and they have a fast path
  for small `Integer`s.
* `Int` and `Int64` variables are C integers where they are only used for
  arithmetic: the parameters of those types (told from the types of the
  functions), and the `let`s of operations on them.  They are no longer
  untagged and tagged again at every operation, which makes a loop on `Int`s
  (a function calling itself in tail position) run about 1.7 times faster.
* All the fixed width integer types (`Int8` to `Int64`, `Bits8` to `Bits64`
  and `Int`) are kept in C integers of their width in this way, and their
  arithmetic, bitwise operations, shifts, comparisons, `case`s on literals
  and casts (between them, and to and from `Integer`, `Double` and `Char`)
  are plain C on those integers, with the same results as before.  A
  `Bits64` above 2^32 was allocated at every operation: a loop of a 64 bit
  hash runs 3 times fewer instructions, a popcount by bit twiddling 9 times
  fewer.  The values are still made (and allocated, for the large `Bits64`,
  `Int64` and `Int`) where they are passed to another function or stored.
* The fixed width integers also cross the calls as C integers: a function
  whose parameters of these types are C integers, or whose result is one
  that it computes, has a worker, a C function that takes and gives the C
  integers, which the calls of the function by name call.  Closures, partial
  applications and the trampoline call the function itself, which unboxes
  the arguments and jumps to the worker.  A hash step called by a loop, a
  PRNG, a non tail recursion on `Bits64` or a mutual recursion with a
  `Bits64` accumulator no longer allocate at every call: they run 5 to 11
  times fewer instructions, and a workload of `Data.HashMap` (`Int` and
  `String` keys, `hashWithSalt` on `Bits64`) 19% fewer.  `--directive
  refc-no-workers` turns this off.
* The functions in `IO` have workers too: a function whose actions take the
  world (`f x = do ...`, which the compiler gives the world as a last
  parameter) takes its fixed width integers as C integers, and gives the
  result of its action as one.  The types of the parameters and results are
  read through aliases (`Hash = Bits64`), newtypes over these types (a
  `record` with one such field) and names of function types (`PrimIO a`).
  A loop in `IO` with an `Int64` state that calls an `IO` step runs 9 times
  fewer instructions and no longer allocates at every step; the sum of an
  `IOArray` of `Bits64` 38% fewer, a loop over a `Bits64` alias or newtype
  9 to 11 times fewer.
* A `mod` or `div` of an `Int`, whose case for zero crashes, gives a C
  integer in the function that computes it: a loop with an `Int` state above
  2^32 that takes a `mod` runs 3.6 times fewer instructions.
* An `Int` literal of more than 32 bits (`0xffffffff`) is a C constant: it
  was an `Integer` converted at each use, as the constant folding leaves the
  casts to `Int` of large values to the backend.
* `Double`s are C doubles too, as the fixed width integers are: the results
  of the primitives on `Double` (arithmetic, comparisons, `sqrt`, `exp` and
  the other functions, the casts to and from the integers), its literals,
  and the parameters and results of the functions (through their workers,
  aliases, newtypes and `IO` included) and of the foreign functions of C
  that take or give a `double`.  A `Double` is allocated only where a value
  is needed: in a constructor or a closure, or as the argument of a function
  that takes a value.  The results are those of the values, NaN, signed
  zeros and the casts out of range included, and so is the rounding on a
  32 bit x86 that computes in more precision (`IDRIS2_DOUBLE`).  A Mandelbrot
  loop runs 25 times fewer instructions, an n-body simulation (the bodies in
  records) 2 times fewer, an update of an array of records of `Double`s 1.3
  times fewer.  `--directive refc-no-unbox-double` turns this off.
* `System.Clock` now reads the clocks with `clock_gettime`: they used to have
  a resolution of a second (`nanoseconds` was always 0), and the monotonic
  clock was the UTC one.
* Strings are now sequences of Unicode code points, like in the other
  backends.  They are still stored as NUL-terminated UTF-8, so the C FFI is
  unchanged, but `length`, `strIndex`, `substr`, `strCons`, `strHead`,
  `strTail`, `reverse`, `pack`, `unpack`, string iterators, `putChar` and the
  casts between `Char` and `String` now work on code points instead of bytes
  (`length "λ"` is 1).  Bytes that are not valid UTF-8 read as U+FFFD.
  `Char` holds a full code point, and casting a number that is not a Unicode
  scalar value to `Char` gives `'\0'`, like in the Scheme backends.
* `show` on a `Double` now gives the same text as the Chez backend: the
  shortest digits that read back as the same number (`0.1`, `1e-10`,
  `0.30000000000000004`, `+inf.0`) instead of `printf`'s `%f`, which printed
  `1e-10` as `0.000000`.  `Double` literals that are NaN, infinite or
  subnormal no longer produce C code that fails to compile.
* Casting a `Double` to a fixed size integer now truncates it and wraps around,
  like in the Scheme backends, instead of being undefined behaviour when it is
  out of range.  Casting to `Int8` no longer fails to compile.
* `Integer` and the type of foreign objects (`CFForeignObj`) can now be passed
  to and returned from foreign functions; they are passed as `Idris2_Value *`.
* A constructor can now take over the memory of a unique value of another
  constructor with as many fields (`Left x` to `Right x`, `Mul a b` to
  `Add a b`), not only of the same constructor, and the fields that keep
  their place are not stored again, with `--directive refc-size-reuse` (off
  by default: GCC takes very long on the code that it gives for some big
  functions).
* Added `RefC` implementations of `Data.Double.epsilon`, `unitRoundoff`, `nan`
  and `inf`.
* Fixed a memory leak when a uniquely referenced constructor is reused: the
  fields that were not used any more were not released.  This leaked the old
  value of every field changed by a record update.
* A `String` returned by a foreign function of the `RefC` calling convention
  now belongs to the caller: it must come from `malloc`, and it is no longer
  copied (and leaked).  This fixes leaks in `pack`, `concat` and
  `Data.Buffer.getString`.  Functions of the `C` calling convention are not
  affected.
* Declare `idris2_fileIsTTY` in `idris_file.h`, so that `isTTY` compiles.
* The main expression runs on a large stack of its own (4GB on 64-bit
  systems, reserved lazily, `IDRIS2_MAIN_STACK_SIZE` to change it) instead of
  the stack of the process.  Much of the library is not tail recursive, so
  sorting or mapping a long list used to crash with a stack overflow, while
  the Chez backend grows its stack as needed.
* Faster generated code, typically by a factor of 2 to 2.5 (the compiler
  itself by about 2.3):
  * Values are allocated from pages of values of the same size, with a free
    list per page, instead of `malloc` and `free`.  Under Valgrind every
    value still comes from `malloc`; for other memory checkers, compile the
    support library and the program with `-DIDRIS2_REFC_NO_POOLS`.
  * A call in tail position no longer allocates a closure: it is stored in a
    pending call that the trampoline of the caller makes.  Applying a shared
    closure to its last argument does the same.
  * A closure has room for all its arguments, so applying one that nobody
    else refers to stores the argument in place, and an application of a
    closure to two arguments is done in one step.
  * The fast paths of reference counting, allocation and the trampoline are
    inlined.
  * Large `Integer` literals are made once instead of being parsed every time
    that they are used.
* Freeing a long list no longer needs a deep stack.
* Faster generated code again, by a factor of 1.4 to 2.1 (the compiler itself
  by about 1.5):
  * The generated C is compiled with `-O2` unless `IDRIS2_CFLAGS` or `CFLAGS`
    say otherwise; it used to be compiled without optimisation.
  * `Int`, `Int64`, `Bits64` and `Integer` values that fit in 32 bits are no
    longer allocated on 64-bit systems, and arithmetic on small `Integer`s no
    longer goes through GMP.
  * A function calling itself in tail position jumps back to its start, and,
    with GCC 15 or later, a call in tail position to a function that does not
    take more arguments than the caller is a jump (`musttail`), instead of
    going through the trampoline.
  * Applying a closure to its last arguments, not in tail position, calls it
    directly.
  * Matching on a constructor that is not used any more frees it without
    touching its fields when it is unique (drop specialisation, as in
    Perceus).
  * Constructors are 16 bytes smaller (a list cell takes 24 bytes instead of
    40), and the constructors without fields are not allocated.
  * The arguments of the primitive operations are borrowed, which saves a
    pair of reference count updates per shared argument.
  * Definitions without arguments are evaluated once, when they are first
    needed, like the top-level constants of the Chez backend (they used to be
    evaluated at every use).
  * A `case` on integers and characters is a C `switch`.
* A `case` on `Int`, `Int64`, `Bits64` or `Integer` constants that do not fit
  in 32 bits chose the wrong branch: the value was truncated to an `int`.
* Casting an `Integer` to a `Double` rounds to the nearest `Double`, like the
  other backends, instead of truncating.
* Casting a `String` to a number reads the whole string as a number, like the
  Chez backend: `"12.7"` gives 12 instead of 0 for an `Integer`, `"12abc"`
  gives 0 instead of 12, and casts to `Int`, `Int64` and `Bits64` are no
  longer limited to 32 bits.
* Strings store their length (and their bytes are allocated with them), so
  they may contain the NUL character
  ([#3161](https://github.com/idris-lang/Idris2/issues/3161)).  C functions
  still receive a C string, which ends at the first NUL.  `putStr`,
  `fPutStr` and `stringByteLength` take the whole string.
* Foreign functions of the `RefC` calling convention take and return a
  `String` as an Idris value (`Idris2_Value *`) instead of a `char *`, like
  `Integer`: the arguments are borrowed, and a result is a new reference.
* Arithmetic on `Int`, `Int8`, `Int16`, `Int32` and `Int64` wrapped around by
  relying on the overflow of signed C integers, which is undefined behaviour
  that an optimising C compiler may exploit: it is now done on unsigned
  integers.
* Decrementing the reference count of a shared closure could make an
  immortal closure mortal again.
* The compiler itself can be compiled with RefC.  Such a compiler has no Chez
  Scheme evaluator (`:set eval scheme` in the REPL).
* Big programs (more than 4MB of C) are compiled in parts by C compilers
  running in parallel (`IDRIS2_CC_JOBS` of them, the number of processors by
  default).  The generated file is still a single file: its definitions are
  in chunks guarded by `#if`, and `-DIDRIS2_PARTS=p -DIDRIS2_PART=i` selects
  the `i`th of `p` parts; without these flags it compiles whole.  Add
  `-flto` (or `-flto=auto`) to the C flags to keep the inlining across parts.
* The units of a big program that the C compilers compile (one file per unit,
  `<name>.u<k>.c`, with the definitions of the unit and the declarations they
  use) are the same when the program is compiled again after a small change,
  and then their object files are reused: a unit is compiled again only when
  its text, the C compiler and its flags (`IDRIS2_CC`, `IDRIS2_CFLAGS`,
  `IDRIS2_CPPFLAGS`), the runtime headers, or the other headers that the
  program includes (and those they include, as `cc -M` lists them) changed
  (texts are compared, not hashed).  `--log compiler.refc.cc:2` tells why
  the object files are not reused.  For that, definitions are put in units
  by their module, the number of units depends only on the size of the
  program (not on `IDRIS2_CC_JOBS`, which only limits the C compilers that
  run at once),
  constants are named after their values instead of numbered, local
  variables are numbered in each function, the numbers that the elaborator
  puts in the names of nested functions and case blocks are made stable, and
  the positions in the source (comments) are left out of the units (but not
  of the single file).  `IDRIS2_REFC_SPLIT_SIZE` (or `--directive
  refc-split-size=N`) lowers the size from which a program is split, to try
  this on small programs.
* Functions borrow the parameters that they only look at: a whole program
  analysis (`Compiler.RefC.Borrow`, after Lean's) finds them, and the callers
  pass them without taking a reference, and release them after the call if
  they were theirs.  The fields of a borrowed value are borrowed too, so a
  function that walks a list or a tree it borrows takes no reference at all.
  A finaliser (`onCollect`) of a value passed to such a function now runs
  once the caller is done with the value, rather than when the function is.
  `--directive refc-no-borrow` turns it off.
* Empty pages of the allocator are used for values of any size, and beyond 16
  of them per OS thread (`IDRIS2_REFC_KEEP_PAGES`) their memory goes back to
  the system; an idle OS thread gives its empty pages to the others.  A
  program that moves from values of one size to another no longer needs the
  memory of both.
* The pages of the allocator are cut from regions of 1MB to 16MB that the
  program maps from the system, instead of being allocated one at a time
  with `aligned_alloc`: glibc gave every page a mapping of its own, twice
  its size, with a system call and about 12% more resident memory than the
  page.  The compiler checks itself with 16% less memory at the peak (232MB
  instead of 278MB), and a program that holds a list of 10 million `Int`s
  needs 242MB instead of 268MB.  On Windows the regions come from
  `_aligned_malloc` (pages could not be allocated there at all before).
* A value with more than 65534 references is freed once they are gone (it
  became immortal).  A constant that needs itself while it is evaluated no
  longer keeps an immortal copy.
* Closures are applied with fewer calls, and an application in tail position
  jumps to the function of the closure with GCC 15 or later.  The calls of
  functions that always return a value skip the trampoline
  (`--directive refc-no-direct-results`), and a closure that a function makes
  and applies once, or applies to its missing arguments one at a time, is not
  made (`--directive refc-no-local-closures`).
* A function that makes a cell of a call to itself (`map`, `++`, `filter`,
  `take`, an `insert` down one path of a tree) loops instead of recursing
  (tail recursion modulo cons): it does not need a stack as deep as the list.
  `--directive refc-no-trmc` turns it off.
* Closures that hold no argument yet, and constructors whose fields are all
  such closures, constants or other static constructors (the dictionary of an
  implementation, say), are static data of the C program instead of values
  allocated every time (`--directive refc-no-static` turns it off).  No
  references are counted for the variables that hold them, nor for string
  constants, and taking or releasing a reference to another immortal value no
  longer calls the runtime (`-DIDRIS2_REFC_SMALL_CODE` in the C flags makes it
  call again, for code that is 10% smaller).  A list comprehension over `Int`s
  runs with 27% fewer instructions.
* An expression that occurs several times inside delayed code is evaluated
  once, the first time that it is needed, instead of every time that it is
  forced (`--directive refc-no-lazy-constants` turns it off).  With the other
  changes of this list, the compiler built with RefC checks the prelude with
  27% fewer instructions.
* A call in tail position of a function that takes more arguments than its
  caller is a jump too (with GCC 15 or later) when the arguments are passed in
  registers.
* The generated C is simpler: a `switch` on the tag of a constructor, no test
  for the only constructor of a type, no reference counting of `NULL` or of
  the values of the small integer types that a `case` looks at, and no dead
  statements after a jump.
* `IDRIS2_REFC_MEMSTATS=1` and `IDRIS2_REFC_LEAKCHECK=1` report the memory of a
  program, and the values that leaked, when it exits; with
  `-DIDRIS2_REFC_STATS` they count the reference count operations, reuses and
  closure applications.  `make install-support-refc-asan` installs a support
  library built with AddressSanitizer.
* A division (`div`, `mod`) of a `Bits`, `Int` or `Integer` by zero stops
  the program with `ERROR: Division by zero` and exit code 1, like a crash
  (the Scheme backends raise an exception), instead of the undefined
  behaviour of C (a `SIGFPE` on x86, or a wrong result).
* The generated C is indented by at most 64 levels: code nested deeper is
  indented like code 64 levels deep.  The text of deeply nested code grew with
  the square of its depth, mostly spaces (code nested 1,800 levels deep made a
  file of 332 MB).
* A string iterator (`Data.String.Iterator` in `contrib`, which the compiler
  uses to hash strings) is a byte offset into the string, like with the other
  backends, instead of a copy of the string behind a pointer with a
  finaliser: making one allocates nothing.  Hashing short strings with
  `Data.String.Iterator.foldl` runs with 17% fewer instructions.
* Strings keep the number of their characters, counted the first time that it
  is needed (or known from the strings that they were made of, or for the
  ASCII string constants), and the characters of an ASCII string are indexed
  directly: `length` takes constant time after the first call, and so do
  `strIndex` and `substr` on ASCII strings, instead of a scan from the start
  of the string every time.  A loop of `strIndex` over a string of 20,000
  ASCII characters runs with 360 times fewer instructions.
* `getLine` no longer leaks the line that it reads (8 KB for every call): the
  support library gave it in a buffer from `malloc`, which the `C` calling
  convention copied into a string and never freed.  It now has a `RefC`
  function of its own, which reads short lines into a buffer on the stack.
  Reading 200,000 short lines takes 15 MB instead of 816 MB, and 0.03 s
  instead of 0.57 s.
* `System.Random` and `System.Future` of `contrib` work with the RefC backend
  (they failed to compile with `FFI not found`).  The random numbers come
  from a xoshiro256** generator of the support library, shared by the
  threads of the program and seeded from the clock unless the program calls
  `srand`.  A future is a green thread, which runs in parallel with the
  others; on the platforms without green threads, its value is computed
  when it is made.
* A C function that is declared to return a `const char *` can be bound with
  the result type `String`: the generated C no longer fails to compile with
  "initialization discards 'const' qualifier" (the C compiler runs with
  `-Werror`).  `idris2_mkString` of the runtime takes a `const char *`.
* Casting a `String` to a `Double` reads the values that are not numbers the
  way `show` writes them, like the Chez backend: `"+inf.0"`, `"-inf.0"` and
  `"+nan.0"` (and `"-nan.0"`), in any case, which all gave 0.0, so that `cast
  (show x)` is `x` for every `Double`
  ([#2261](https://github.com/idris-lang/Idris2/issues/2261)).  Other
  spellings (`"inf"`, `"nan"`, `"Infinity"`) are still 0.0, as with Chez.  As
  the compiler built with RefC folds constants with this cast, the cast of a
  literal changes the same way for every backend.
* On 32 bit platforms
  ([#1617](https://github.com/idris-lang/Idris2/issues/1617)): a cast from
  an `Integer` that does not fit in 32 bits to `Int`, `Int64` or `Bits64`
  kept its low 32 bits only (the runtime read it as an `unsigned long`), and
  so did a `String` cast to these types; a `Char` above U+FFFF lost its
  upper bits (unboxed values had 16 bits; they have 24 now).  The generated
  C compiles there as the compiler compiles it, with `-Werror` (shifts of a
  pointer by 32 bits, in code that only 64 bit platforms run, were errors),
  with or without `UINTPTR_WIDTH`, and with GCC 15 for 32 bit x86 and ARM,
  where a call in tail position cannot always be a jump (`musttail`): the
  calls go through the trampoline there.  The test `refc/bits32_001`
  compiles the C code of a program with `cc -m32` where that works, as the C
  code does not depend on the machine of the compiler; there is no 32 bit
  build of the compiler itself.
* Casting a fraction with a zero denominator (`"1/0"`, `"-3/0"`, `"0/0"`)
  from a `String` to an `Integer`, a fixed width integer or a `Double` no
  longer kills the program with `SIGFPE`: it is no number, and gives 0 or
  0.0, as with the Chez backend.
* Casting a `Double` between -2^64 and -9.2e18 to `Int`, `Int64`, `Bits64`
  or a narrower integer gives the exact value wrapped around, as with the
  Chez backend: it was off by up to 1024 (`cast {to = Int}
  (-9223372036854774784.0)` gave -9223372036854775808, and as an `Int32` 0
  instead of 1024).
* Casting a fraction from a `String` to a `Double` gives the `Double`
  nearest to it, as with the Chez backend, instead of the one towards zero
  (`"1/10"` gave 0.09999999999999999, `"1/5"` 0.19999999999999998).
* Casting a NaN or an infinite `Double` to an `Integer` gives 0, as the
  casts to the fixed width integers do, instead of killing the program with
  `SIGFPE` (the Chez backend raises an exception).
* `show` on a `Double` gives the shortest digits that read back as the same
  number also when they are not the nearest to it, as with the Chez backend:
  46 powers of two were shown with 17 digits instead of 16 (2^172 as
  `5.9863107065073784e51` instead of `5.986310706507378e51`).
* Shifting an `Integer` by a count of 2^64 or more (`prim__shl_Integer`,
  `prim__shr_Integer`) no longer shifts by the count's low bits: a shift
  right gives 0 or -1, a shift left of 0 gives 0, and a shift left of any
  other number is an error, `ERROR: Integer shifted left by too many bits`
  (the Chez backend runs out of memory).

#### Chez Backend

* Backtraces: a program that dies of a fatal error (`idris_crash`, a missing
  case in `partial` code, or an error that Chez raises and nothing handles)
  can print the Idris
  functions of its continuation on stderr, after the message, in the same
  form as with RefC.  `--directive chez-backtrace` puts the Idris names of the
  functions and where they are defined in the program, keeps Chez from
  inlining them (2% to 18% more instructions on `benchmark/`), and turns the
  backtraces on; `IDRIS2_CHEZ_BACKTRACE=1` or `0` turns them on or off when
  the program runs.  Without the directive, the code of the program is the
  same with them on or off; the continuation is only walked when the error
  happens.  See "Backtraces" in the Chez documentation.
* A crash (`idris_crash`, a missing case) on a thread other than the main one
  ends the program with exit code 1, as on the main thread: `exit` of Chez
  only ended that thread, and the program went on, or waited for it for ever.

* In incremental builds, every module has its own script to compile its
  Scheme code (next to its `.ss` file) instead of a `compileChez` file shared
  by the whole package: with modules built in parallel, a module could run
  the script of another one, or a half-written one ("variable cs.ss is not
  bound"), which broke `make bootstrap` and `make libs IDRIS2_CG=chez`.
* `shiftR` of a signed fixed width type (`Int8` to `Int64`, `Int`) by a
  negative count, which is a left shift, wraps around like the other
  operations of the type: `prim__shr_Int8 100 (-1)` gave 200, now -56 (as with
  RefC).  A shift by a huge count (`prim__shl_Int 1 9223372036854775807`)
  gives 0 instead of running out of memory.  The Racket and Gambit backends
  share this code and have the same helpers.
* `prim__negate_Int8` to `prim__negate_Int64`, `prim__negate_Int` and
  `prim__negate_Bits8` to `prim__negate_Bits64` wrap around: the negation of
  -128 as an `Int8` is -128 (it was 128), that of 200 as a `Bits8` is 56 (it
  was -200).  (`negate` of the `Num` implementations, which is `0 - x`, was
  right.)  The same for the Racket, Gambit and JavaScript backends.
* `getLine` no longer leaks the line that it reads (120 bytes for a short
  line): `idris2_getStr` of the support library gave it in a buffer from
  `malloc`, which the `C` calling convention copied into a string and never
  freed.  It now gives it in a buffer of the thread, valid until the next
  call (the previous line is freed).  The Racket and Gambit backends, and the
  checked-in bootstrap code, use the same function.
* A `String` or `Buffer` argument of a C function no longer moves while the
  function runs.  Chez passed it as the address of a bytevector in the Scheme
  heap, which a collection could move or free when the C function called back
  into Idris (or, for `__collect_safe`, when another thread collected), so C
  then read another object or crashed.  The bytevector is now locked during
  the call.  It costs about 100ns per call with a `String` argument: a call
  of `strlen` from an Idris loop takes 450ns instead of 350ns on a 16 byte
  string, and 3% more on a 1KB one.
  The test `chez/ffiPin001` collects in a callback.
* The calling convention `C__scoped_callbacks` (`%foreign
  "C__scoped_callbacks:qsort,libc" "C:qsort,libc"`) is for a C function that
  only calls its callbacks before it returns: the code made for each callback
  is freed after the call.  With `C`, it is locked for ever, since C may keep
  the callback, so each call of a function that takes one kept about 400
  bytes (20,000 calls of the test `chez/ffiScoped001` keep 8MB with `C`,
  nothing with `C__scoped_callbacks`).  The other backends take the `C`
  specifier.
* `--cg chez-sep` (separate compilation: every namespace group is a Chez
  library of its own, compiled again only when it changed) works again: it
  made no program at all.  Since a refactoring of 2023 its compile commands
  (`echo '...' | chez`) went through the escaping version of `system`, which
  quoted the `|`, so Chez never ran, and the empty `.so` files that `touch`
  made were all that there was (`failed for ... mainprog.so: no such file or
  directory`).  The compile scripts are now files that Chez runs with
  `--script`, and the compiler stops with Chez's error when one fails.  The
  rebuild is also right now: a unit that imports one that changed is compiled
  again too (Chez refuses it otherwise, "requires a different compilation
  instance"), as is every unit when the support library changed; the hash of
  a unit is kept once Chez has compiled it, and a unit whose `.so` file is
  missing is compiled again.  The start script for Windows no longer runs the
  program twice.  The tests `chezsep/chezsep001` to `chezsep004` (hello world,
  base and contrib, rebuilds, backtraces) run when Chez is there; there were
  none.
* A program that dies of a fatal error with backtraces on (see above) no
  longer eats the memory of the machine when it cannot write them (stderr
  closed, or a full disk, or `| head`): the error of the write reached the
  handler that prints the backtrace, which wrote, failed, and started again.
  Such an error is now ignored, and the program ends with its exit code (1, or
  255 after an error of Chez).  The test `chez/backtraceCrash001` no longer
  depends on the place of `idris_crash` in `Builtin.idr` and of the missing
  case of `div` in the Prelude, on what Chez inlines without the directive,
  or on the thread that dies getting the CPU within two seconds.

#### JavaScript Backends

* Deep recursion and loops through monads no longer overflow the small stack
  of JavaScript (about 1MB) at a few thousand iterations; see the section
  on the stack depth in the documentation of the backends.
  + Tail calls to functions that are not known statically (the continuation
    of `>>=` in `Maybe`, `Either` or an unknown monad, continuation-passing
    code) go through a trampoline, with Node and in the browser: a `do`
    loop in `Maybe` overflowed at 2800 iterations, and runs 10^6 (13 times
    faster than the 300,000 it could do on a big stack).  The cost on the
    benchmarks is from -30% (`mergeStr`) to +40% (`triples`) instructions;
    `--directive no-trampoline` turns it off.  Function arguments of foreign
    functions are wrapped to run the pending calls of their results.  No
    pending call reaches JavaScript code: an Idris function that it calls
    otherwise (a closure in an `AnyPtr` or a record, stored by JavaScript
    and called later, from the event loop) makes its tail calls directly,
    where it returned an object of class `__TC` after 64 nested calls; and an
    exception thrown through such calls no longer leaves them counted (which
    made the closures above fail after it, or the stack grow).  JavaScript
    code can call such a function through `__resFn` to get the trampoline.
    The same function given to foreign code gets the same wrapper every
    time, with the `length` of the function (each call made a new one, of
    length 0, so `removeEventListener` could not remove a listener).
  + With Node, the main expression runs on a stack of 1GB in a worker
    thread, as with RefC, so that recursion that is not a tail call
    (`foldr`, `sort`, `traverse` on lists of 10^6 elements) works: four of
    the five benchmarks overflowed the stack before.  `IDRIS2_MAIN_STACK_SIZE`
    sets the size (`0` runs on the main thread).  The browser keeps its
    limit for such recursion.
* `getChar` with Node reads file descriptor 0 instead of `process.stdin.fd`.
* The smallest Double literals (subnormal numbers, `4.9e-324`) were 1 in the
  generated code, and a negative constant after an operator (`x - (-5)` on
  `Integer`) made a syntax error.
* A toplevel function whose only tail calls are to itself is compiled to a
  `while` loop instead of going through `__tailRec`, which allocated an object
  per round: 5 to 25% fewer instructions on the benchmarks with Node
  (`mergeInt` -23%, `triples` -25%).
* In the browser (`--cg javascript`), functions with tail recursion modulo
  cons (`zipWith f (x :: xs) (y :: ys) = f x y :: zipWith f xs ys`) are
  compiled to loops that make the cell first and fill it later, so that
  `zip`, `zipWith`, `take`, `intersperse`, `sort`, `lines`, `words` and the
  like (and such functions of programs) no longer overflow the stack at a
  few thousand elements.  `--directive no-trmc` turns this off; with Node,
  whose main expression has a large stack, it costs 8 to 15% on the
  benchmarks and is off unless `--directive trmc` is given.
* In the browser (`--cg javascript`), the other functions that call
  themselves where the call is not a tail call are compiled to loops on an
  explicit stack in the heap: a call in an argument, a `case` scrutinee or a
  `let` value pushes a frame with what is left to do after it, and the loop
  goes on with the call.  So `foldr` on lists, `traverse`, `for` and
  `sequence` on lists in `Maybe` and `Either`, `span`, `break`, `splitAt`,
  `partition`, `unzip`, `group`, `findIndex` and the like, the `treeInt`
  benchmark and such functions of programs no longer overflow the stack at
  a few thousand elements.  With this, the loops of tail recursion modulo
  cons through a `case` in a field (`tails`) and the library changes below,
  of 90 library functions run on 10^5 elements in the browser 27 overflowed
  the stack, now 2 (`traverse` in `State`, `foldr (*>)` in `IO`).  The
  order of evaluation stays the same (a call where it would not stays a
  recursion).
  `--directive no-explicit-stack` turns this off; with Node it is off unless
  `--directive explicit-stack` is given.  It costs nothing measurable on the
  benchmarks (with `--directive trmc` on Node), 5 to 8% on lists of 1000
  elements and 2.4 times the instructions on `fib`; on 10^6 elements it takes
  72 to 87% fewer instructions than Node's recursion on its large stack.
* Node: `getLine` dropped no newline at the end of the line, `fEOF stdin` was
  never true (stdin was a new object at every use), and `fGetChar`,
  `fGetChars`, `fPoll`, `sleep`, `usleep`, `getEnvironment`, `enableRawMode`
  and `resetRawMode` had no implementation; `fPutStr` of an empty string
  failed, and `strerror` gave no message.  A line is no longer read with a
  copy of the line per byte, and a file open for reading only is read in
  chunks: the benchmarks that read files take 53% (`mergeStr`) and 20%
  (`spellcheck`) fewer instructions.
* Node: `System.Signal` works (it did not at all): the signals are received
  by the main thread and seen by `handleNextCollectedSignal` at once while
  `main` runs in its worker thread; on the main thread, only once `main`
  returns.  See the section on signals in the documentation of the backends.
* Node: foreign code that reads `process.stdin` as a stream gets the input
  when `main` runs in its worker thread.
* Node: `Data.Buffer` has `getInt8`, `setInt8`, `getInt16`, `getInt64` and
  `setInt64` (it had none, so a program that used them did not compile), and
  `setByte` wraps its value to a byte as the other backends do; every accessor
  gives the bytes and values of Chez and RefC.  `setInt` and `getInt` take
  eight bytes, as with the others (they took four, as `Int` has 32 bits with
  JavaScript): `setInt` writes the value sign-extended to 64 bits, so a
  negative `Int` reads back as the same `Int64` and the same `Int` with every
  backend, and `getInt` reads the low 32 bits.
* Node: `popen`, `pclose` and `popen2` start a child process with pipes that
  runs at the same time as the program (`popen` for writing and `popen2` did
  not exist, `popen` for reading ran the command first and gave it no stdin),
  and `popen2Wait` returns its exit status.  The pipes are FIFOs that the
  program opens itself, instead of the pipes of Node's child process, whose
  file descriptor is not part of Node's API.  With
  `IDRIS2_MAIN_STACK_SIZE=0` they work too (`popen2` and `popen` for writing
  stopped the program with an error, `popen` for reading ran the command to
  its end first): a small Node process waits for the child and passes its
  exit status on.
* JavaScript: `fork`, `threadWait` and `System.Future` stop the program with a
  message (a program that used them did not compile); `Mutex`, `Semaphore`, `Barrier`, `Channel`, `Condition` and the
  thread data of `System.Concurrency` work for a program with one thread, and
  what would wait for another thread stops it with a message instead of
  hanging.  See the section on threads in the documentation of the backends.

### Library changes

* Ranges (`[x..y]`, `[x,y..z]`) are built by loops instead of `takeUntil`
  and `takeBefore` on a `Stream`, and `traverse_`, `for_` and `sequence_` on
  lists in `IO` are transformed (`%transform`) to a loop that passes the
  world on (`ioTraverseList_`) instead of building a chain of `*>`.  They no
  longer need a stack as deep as the list with JavaScript, and are faster with
  every backend: `length [1..10^6]` takes 63% fewer instructions with Chez and
  32% fewer with RefC, `for_ [1..10^6]` in `IO` 80% and 61% fewer.
* `traverse`, `for` and `sequence` on lists in `IO` are transformed
  (`%transform`) to a loop that passes the world on and collects the results
  in a `SnocList` (`ioTraverseList`), and `foldlM` on lists in `IO` to one
  that passes the accumulator on (`ioFoldlMList`), instead of building a
  chain of `<*>` or `>>=` as long as the list and running it nested.  They no
  longer need a stack as deep as the list with JavaScript, and are faster with
  every backend (10 times a list of 10^6 elements): `traverse` 81% fewer
  instructions with RefC and 76% with Chez (peak memory 349MB to 52MB, 430MB
  to 102MB), `sequence` 55% and 56%, `foldlM` 59% and 90%.
* `traverse`, `for`, `sequence`, `traverse_`, `for_` and `sequence_` on lists
  in `State` (`StateT s Identity`) are transformed (`%transform`) to loops
  that pass the state on (`stateTraverseList`, `stateTraverseList_`), and
  `*>` in `IO` and in `State` to a function that runs its second action as a
  tail call (`ioSeqRight`, `stateSeqRight`).  `traverse` in `State` and
  `foldr (*>) (pure ())` in `IO` built a chain of closures as long as the
  list, each of which called the next one before it returned, and overflowed
  the stack of the browser at a few thousand elements.  Of 89 library
  functions run on 10^5 elements in the browser, 5 overflowed the stack
  (`traverse` and `traverse_` in `State`, `foldr (*>)` in `IO` and in
  `State`, `traverse` in `Writer`) and 2 ran for minutes (`concat` and
  `concatMap` of a list of lists, whose rule did not apply for the reason
  above); now only `traverse` in `Writer` overflows.  Faster with every
  backend, too: `traverse` in `State` on 10^6 elements takes 65% fewer
  instructions with Chez, 52% with RefC and 98% with Node, `foldr (*>)` in
  `IO` 32%, 34% and 67% fewer.
* `traverse`, `for`, `sequence`, `traverse_`, `for_`, `sequence_` and
  `foldlM` on lists, and `*>`, in `Reader`, `Writer`, `RWS` (over
  `Identity`), in `StateT`, `ReaderT`, `WriterT` and `RWST` over `IO`, in
  `StateT` over `Either e` and `Maybe`, and `foldlM` in `State`, are
  transformed (`%transform`) to functions that do the same with `>>=`, where
  the rest of the list is the continuation (`bindTraverseList`,
  `bindTraverseList_`, `bindFoldlMList`, `bindSeqRight` in
  `Control.Monad.Trans`, for any monad); in `EitherT e IO` and `MaybeT IO`,
  whose `<*>` runs both actions also after a `Left` (`Nothing`), `traverse`
  and friends run the actions in a loop in `IO` and combine their results
  after, and `*>` runs its second action as a tail call after a `Right`
  (`eitherTSeqRight`, `maybeTSeqRight`).  `traverse` and friends on lists in
  `Control.App` are loops of `bindApp` (`appTraverseList`,
  `appTraverseList_`); `traverse_`, `for_`, `sequence_` on `SnocList`,
  `List1` and `Vect`, and `traverse`, `for`, `sequence` on `SnocList` and
  `List1`, in `IO` are transformed to the loops on lists in `IO`; `many` of
  `Data.String.Parser` (and `some`, `takeWhile`, `takeWhile1`, `spaces`,
  which use it) is a loop.  The results and the order of the effects are
  those of the chains of `<*>` and `*>` (test `allbackends/applchain001`,
  `allbackends/applchain002`, `node/applchain_browser`).  They built a chain
  of closures as long as the list, each of which ran the rest before it
  returned, and overflowed the stack of the browser at a few thousand
  elements: of 172 shapes (`traverse` and friends, `foldr (*>)`, `foldr (<*)`,
  loops through `when` and recursive loops in 14 monads; containers;
  parsers; `Control.App`) on 10^5 elements in the browser, 101 overflowed;
  now 20 do (`foldr (<*)` in 11 monads, `traverse` on `Vect` in `IO`, the
  containers in `State`, `many` and `some` of `Text.Parser`; see the
  documentation of the JavaScript backends).  Faster with the other back
  ends too (`perf stat -e instructions:u`): on 10^6 elements, the 22 cases
  measured take 41% to 90% fewer instructions with Chez (`traverse` in
  `StateT s IO` 81%, in `Writer` 46%) and 1% to 51% fewer with RefC
  (`traverse` in `StateT s IO` 32%, in `Writer` 13%, `foldlM` in `StateT s
  IO` 1%).
* `and` and `or` on lists are transformed (`%transform`) to loops (`listAnd`,
  `listOr`) that force the elements in the same order: through the `foldMap`
  of `Foldable List` they built a chain of `&&` (`||`) as long as the list,
  and forcing it needed a stack as deep as the list with JavaScript.  `and`
  on 10^6 elements takes 59% fewer instructions with RefC, 53% with Chez and
  63% with Node.
* `toList` of a `SortedMap` (and of a `SortedDMap` and `SortedSet`) builds
  the list from the right instead of with a continuation per element, which
  nested a call per element and overflowed the stack with JavaScript at
  some 10^4 elements; with Node it takes half the instructions.
* `concat`, `concatMap` and `foldMap` over a list take time linear in the
  size of the result for the `List`, `String` and `SnocList` monoids, however
  they are called.  `Foldable List` did a left fold, which copies the
  accumulator at every step for `List` and `String`, and the `%transform`
  rules for `concatMap` and `concat` only applied where the element type was
  known and the call fully applied: through a function with `Foldable t` and
  `Monoid m` constraints, or partially applied, 40,000 lists of two elements
  took 48G instructions with RefC (74G with Chez), sixteen times that for
  160,000, and now 19M (the same for any way of calling).  `Monoid` has a new
  method, `foldMapListImpl : (a -> ty) -> List a -> ty` (`foldMap` of a
  list), which `foldMap` of `Foldable List` calls:
  `List` builds the result with a loop (`listBindOnto`) and `String` with
  `fastConcat`.  The rules of `listConcat`
  and `listConcatMap` are gone (the method does the same), those of
  `fastConcat` and `fastConcatMap` stay.  The `Foldable` instances of
  `SnocList`, `Vect` and `List1` give their elements to the method too
  (`foldMap` of a `List1` or `Vect` was quadratic for `List` and `String`, and
  that of a `SnocList` for `String` and `SnocList`; for a `Vect` and a cheap
  monoid it now costs a conversion to a list).  The default of the method,
  `foldMapListBalanced`, is for the monoids that wrap a list, a string or a
  snoc list in a type of their own (a `newtype`, a log record with a field of
  lists, a document, a pair of lists), which the left fold of before made
  quadratic: it combines the pieces in chunks of 16 from the left, and the
  chunks as a binary counter does (a stack of partial results, the two on
  top combined as long as their number is even, the stack combined from the
  top at the end), with the same order of operands and, for a `<+>` that is
  associative, the same result; a list of 16 pieces or fewer is combined
  from the left as before, with `neutral` at the left end, and the stack
  has `O(log n)` entries, so it needs no more stack than a loop.  It costs
  `O(n log n)` for `n` pieces whose `<+>` copies its left or its right
  argument, where the left fold took `O(n^2)` for one of them and `O(n)` for
  the other (a newtype over a `SnocList` of 10^6 pieces: 473M instructions
  with RefC and 836M with Chez before, 776M and 1.6G now), and the same
  number of calls of `<+>`.  A newtype over `List Int` of 40,000 pieces took
  24.0G instructions with RefC and 30.4G with Chez, now 37M and 272M (10^6
  pieces: 0.97G and 1.9G); a record with a counter and a `String` 513M and
  2.5G, now 86M and 404M; a pair of lists 72G and 133G, now 81M and 336M.
  A monoid whose `<+>` costs no more than a few instructions pays for the
  stack: with 10^6 pieces, a record around an `Int` that adds takes 372M
  instructions with RefC and 468M with Chez before and 382M and 555M now,
  one around a `Bool` that `||`s 314M and 469M before and 379M and 557M now.
  `Additive`, `Multiplicative`, `Ordering`, `Any` and `All` (the ones of
  `any`, `all`, `and` and `or`), `Maybe`, `SnocList`, the maps and sets of
  `Data.SortedMap`,
  `Data.SortedSet`, `Data.SortedMap.Dependent`, `Data.HashMap` and
  `Data.HashSet` keep the left fold, `foldMapListGo f neutral`, in their
  `foldMapListImpl`, as it is the best for them (a union of sets is 4 times
  as slow with the balanced one), and so can a user monoid like them.  The
  constructor `MkMonoid` takes the method as a second argument, so a use of it
  must pass one: `\f => foldMapListBalanced @{sg} f z` for the semigroup
  `sg` and the neutral element `z`.  A `<+>` that is not associative gives
  another result from the 17th piece on (the nesting of the balanced fold is
  not specified).  New public names:
  `foldMapListImpl`, `foldMapListGo` (the left fold), `foldMapListBalanced`
  and `concatStrings` (`fastConcat` that reduces at compile time,
  transformed to it).
* Arrays (`Data.IOArray`, and `Data.Linear.Array` of `contrib`) are cheap
  enough to build data structures on.  Reading and writing an element were
  calls through the `HasIO` dictionary that built closures for the action
  (and, for the linear arrays, a call of `unsafePerformIO`); at a known
  implementation they are now specialised (`%spec`) and inlined to the
  primitive and its bounds check.  Copying is done by the backend (the new
  primitive `prim__arrayCopy` of `Data.IOArray.Prims`) instead of an Idris
  loop of reads and writes.  In instructions per element, for an array of
  1024 `Int`s, RefC / Chez: read 551 → 134 / 143 → 73 (the loop around it
  alone takes 39 / 52), write 1353 → 191 / 310 → 83, copy 1799 → 36 /
  404 → 33; through `Data.Linear.Array`: read 701 → 157 / 155 → 102, write
  1628 → 242 / 312 → 112, `copyArray` 2813 → 45 / 580 → 37.
* The `HasIO` functions of `Data.IORef` and `System.Concurrency` are
  specialised (`%spec`) on their `HasIO` implementation: at `IO`, they are
  direct calls of the primitives instead of going through the `Monad`
  implementation at runtime.  A loop of `modifyIORef` runs 4 times faster.
  So are those of `System`, `System.File` and `System.Directory` (except
  `usleep` and `readLinesOnto`): reading a file line by line with `fGetLine`
  runs 3 times faster, writing one with `fPutStr` 4.5 times faster.
* `network`, with every backend: `accept` no longer leaks the text of the
  IPv4 address of the peer (`idrnet_sockaddr_ipv4` gives it in a buffer of
  the thread instead of one from `malloc`), `bind` and `sendToBuf` no longer
  leak the result of `getaddrinfo`, and `accept` on a Unix socket no longer
  reads the uninitialised path of an unnamed peer (it is `""`).

#### Base

* `Data.IOArray` has `newFlatIO`, `readFlatIO` and `writeFlatIO`,
  `newFlatArray`, `readFlatArray` and `writeFlatArray` at `IO`.

* Added `copyArrayRange` to `Data.IOArray`, which copies a range of an array
  to another one or to another place in the same one (the ranges may
  overlap), and `prim__arrayCopy` to `Data.IOArray.Prims`, which it calls;
  `newArrayCopy` uses it too.  `newArray` with a negative size makes an empty
  array, instead of crashing.
* `system` returns 128 + the number of the signal for a command killed by a
  signal (143 for `SIGTERM`), as shells report it: it returned -1, which
  lost the signal (and, with the JavaScript backends, `null`).  It still
  returns the exit code of a command that exits, and -1 when the command
  could not be run at all.
* `sort`, `sortBy` and `mergeBy` of `Data.List` are specialised (`%spec`) on
  their comparison (`sort` on its `Ord` implementation), and `sortBy` splits
  its list without making a closure for every element: sorting a list of
  `Integer`s runs with 29% fewer instructions with the RefC backend (34%
  with `--spec-interfaces`), 22% fewer with Chez.
* `getStringAndFree` (used by `fGetLine` and `fGetChars`) and
  `currentDir` copy the C string before they free it: once specialised at
  `IO` and inlined, the copy, which was pure, could be made after the call of
  `free`, and read freed memory.
* `readFilePage`, and so `readFile`, no longer use stack space for every line
  that they read: the recursion went through the bind of the composition of
  `io` and `Either`, which is not a tail call.
* Added `emptyBuffer` to `Data.Buffer`
* Added `rtrim` to `Data.String`.
* Added `decToMaybe`, `maybeCong` and `maybeCong2` to `Data.Maybe`.
* Added `maybeEq` to `Decidable.Equality`.
* Removed `writeIORef1`, which unsafely allowed a linear value to become unrestricted.
* Made `xs` and `ys` explicit arguments of `SplitRecPair` in `Data.Vect.Views`.
* Implemented core interfaces for `Data.Singleton`
* `fromList` and `toList` for `Data.Vect` rewritten so that they are optimized away during codegen.
* Reduced the fixities of `Data.Record` operators `:-:`, `:-` and `:+` to 0.
* Reading a file that fails (a directory, `EISDIR`) returns an error:
  `fGetLine` returned an empty string without an error, so `readFile`,
  `readFilePage`, `fRead` and the other loops that read until the end of the
  file never stopped (`idris2 --check` on a directory named `Foo.idr` hung,
  once the compiler is built with this `base`).  `replWith` and `repl` stop
  on an error of `stdin` too.

#### Contrib

* `Data.Linear.Array.Flat`: linear arrays laid out by the `Flat` of their
  elements (see `Data.IOArray.Flat`), `FlatArray` and `FlatIArray`, with the
  functions of `Data.Linear.Array` under the same names (`mread`, `write`,
  `msize`, `mcopy`, `toIArray`, `read`, `size`), `newFlatArray` and
  `thawFlat`.  A program moves to them by importing the module, writing
  `FlatArray` and `FlatIArray` for `LinArray` and `IArray`, and making its
  arrays with `newFlatArray` (qualified as `Flat.newFlatArray` where
  `Data.IOArray` is imported too); `Data.Linear.Array` is unchanged.  With
  RefC, their elements are inline.  The test `allbackends/flatlinear001`.

* `Data.Linear.Array`: added `copyInto`, which copies a range of an immutable
  array into a linear one, and `thaw`, which makes a linear copy of an
  immutable array (with `write` and `toIArray`, an updated copy, as the nodes
  of a persistent data structure need); `MArray` has a new method `mcopy`,
  with a default that copies element by element, which `LinArray` implements
  in bulk and `copyArray` uses.
* Added `Data.ByteString`, an immutable sequence of bytes: a slice
  (buffer, offset, length) of a `Data.Buffer` that is never written after it
  is built, so that `take`, `drop`, `splitAt`, `span` and `split` take constant
  time (or time in the length of the part found) and share storage, and
  `copy` releases a large parent buffer.  It has `pack`/`unpack`, `index`,
  `head`/`last`/`uncons`/`unsnoc`, `append`/`concat` (one allocation),
  `cons`/`snoc`, `reverse`, `map`, `foldl`/`foldr`, `any`/`all`, `elem`,
  `findIndex`, `isPrefixOf`/`isSuffixOf`/`isInfixOf`, `split`, `replicate`,
  16, 32 and 64 bit reads in both byte orders (`indexBits32BE`...), `Eq`,
  `Ord` (lexicographic, unsigned), `Show`, `Semigroup`, `Monoid` and
  `FromString`.  `fromString`/`toString` are UTF-8 and give the same
  answers with every backend: `toString` returns `Nothing` for invalid input
  (truncated or stray bytes, overlong forms, surrogates, above U+10FFFF) and
  `toStringLossy` replaces each invalid byte with U+FFFD, whereas the
  primitive `Data.Buffer.getString` replaces invalid bytes with U+FFFD but
  with a different number of replacement characters per backend (a
  truncated three-byte sequence gives one with Chez and Node, two with
  RefC; a surrogate gives one with Chez, three with RefC and Node).  `toHex`/`fromHex` encode and decode
  hexadecimal.  The unsafe code (`unsafePerformIO` over fresh buffers) is
  confined to `Data.ByteString.Internal`, which `Data.ByteString` does not
  re-export: a program that imports `Data.ByteString` sees the type and the
  safe functions only (the type is in `Data.ByteString.Types`).  A buffer
  that cannot be allocated stops the program with an out-of-memory message.
* Added `Data.ByteString.Builder`, which builds a `ByteString` from bytes,
  integers of 8 to 64 bits in both byte orders, byte strings and UTF-8
  strings in time linear in the size of the result, however the pieces are
  nested, and with one allocation.
* Added `System.File.ByteString`: `readFile`, `writeFile`, `appendFile`,
  `hGet` (up to `n` bytes), `hGetContents` and `hPut`.
* Added hash maps and hash sets to `contrib`:
  `Data.Hashable` (an interface `Hashable` with `hashWithSalt` and `hash`,
  with instances for the fixed-width integers, `Int`, `Integer`, `Nat`, `Char`,
  `String`, `Bool`, `Double`, `()`, `Ordering`, `Fin`, tuples, `Maybe`,
  `Either`, `List`, `Vect`, `SnocList` and `List1`; the hashes are numbers of
  31 bits, made with FNV and the finaliser of a 32-bit integer hash with
  `Int` arithmetic, so that it stays on machine words on RefC and in fixnums
  on Chez, and they are the same on the Chez, RefC and JavaScript back ends,
  apart from `Int`, which has 32 bits on JavaScript, and strings with
  characters outside the Basic Multilingual Plane there; `Data.ByteString` has
  the instance for `ByteString`, which hashes the bytes and the length and is
  the same on every back end, and `Data.Hashable` does not depend on it),
  `Data.HashMap` (a
  persistent hash trie of eight-way nodes with collision buckets, with the
  interface of `Data.SortedMap`: `insert`, `insertWith`, `lookup`, `delete`,
  `update`, `fromList`, `foldrWithKey`, `mapWithKey`, `filter`, `mergeWith`,
  `Functor`, `Foldable`, `Traversable`, `Semigroup`, `Monoid`, `Show` and an
  `Eq` that does not depend on the order of insertions; `size` takes time in
  the size of the map) and `Data.HashSet`.  They are total and use no unsafe
  operation.  They need fewer instructions than `Data.SortedMap` for the
  insertion, the lookup and the deletion of 100000 and 1000000 keys, `Int` and
  `String`, with RefC (17 to 59% fewer) and Chez (16 to 48% fewer), measured
  with `perf stat`, and 10 to 50% more memory.
* The Chez back end no longer makes the masks of the fixed-width arithmetic
  (`2^bits - 1`, big numbers for 64 bits) when the result of an operation on
  61 bits or more is a fixnum, nor for the cast of a non-negative fixnum to
  `Bits64`: an addition of `Int`s took 400 instructions and takes 40.
